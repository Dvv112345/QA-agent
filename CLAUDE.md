# CLAUDE.md

## Project Overview

QA Agent manages LLM-assisted QA of GitHub repositories — FastAPI + PostgreSQL backend, React + Vite frontend. Register a **repo**, create a **sprint** against it (captures the README plus a filtered file tree as LLM context for every later stage), then walk the sprint through four stages:

1. **Requirements** — typed into a form or split from an uploaded PRD; an LLM checks each for QA-clarity through a clarification Q&A loop until confirmed.
2. **Test environment access** — free text describing how to reach the running app, judged synchronously by the LLM and extracted into structured, editable environment variables.
3. **Test plans** — one per requirement, generated by an RQ worker from the requirement alone (deliberately code-blind), refined by feedback or direct edit until approved.
4. **Runs** — two parallel modes behind the same gate: **scripted execution** (one Playwright script per test case, run in a subprocess, self-healing script bugs via an LLM diagnosis loop) and **exploratory testing** (an LLM driving a real browser through SBTM charters).

Verified scripts can then be **exported to the repository's own CI** as a pull request (see [CI/CD export](#key-flows)) — a side door off the run stage, not a fifth stage.

Both run modes emit **findings** in one vocabulary — `bug` (the product is wrong) vs `issue` (testing was obstructed). Bug findings are grouped into the sprint's distinct **defects**, optionally filed one-ticket-per-defect to a connected **Jira project or GitHub Issues repo**, and counted in a per-sprint **QA metrics** panel. See [Key flows](#key-flows).

## Commands

Backend commands run from the repo root; frontend commands from `frontend/`.

| Command                                 | Purpose                                                                           |
| --------------------------------------- | --------------------------------------------------------------------------------- |
| `pip install -e ".[dev]"`               | Install backend + dev dependencies                                                |
| `python -m backend.main`                | Start API server at http://localhost:8000 (docs at `/docs`)                       |
| `python -m backend.worker`              | Start an RQ worker (one per terminal; more workers = more concurrency)            |
| `python -m backend.scripts.clear_queue` | Empty the RQ queue and job registries                                             |
| `python -m backend.scripts.reset_db`    | Drop + recreate all tables (`--yes` skips prompt, `--with-storage` wipes uploads) |
| `python -m pytest -v`                   | Run all backend tests (`-k <keyword>` to filter)                                  |
| `npm install` / `npm run dev`           | Install frontend deps / Vite dev server at http://localhost:5173                  |
| `npm run build` / `npm run lint`        | Type-check (`tsc -b`) + build / ESLint                                            |
| `npm test` / `npm run test:watch`       | Vitest (single run / watch mode)                                                  |
| `pre-commit install`                    | Install git hooks (first time only)                                               |

**Prerequisites for running the backend:**

- PostgreSQL with a `qa_agent` database (`createdb qa_agent`) and `backend/.env` present (copy from `backend/.env.example`). Tables are auto-created by `init_db()` at startup.
- Every LLM stage (requirement analysis, test planning, execution, exploratory) additionally needs Redis, a worker in a second terminal, and `OPENAI_API_KEY`. Without them rows simply stay `pending`.
- The worker host also needs `playwright install chromium` run once — the pip package doesn't include the browser binary.
- Tests need none of the above (see [Testing](#testing)).

**Navigation is layout-level, not per page.** Every page gets the same three rows above its content — breadcrumb, `FinishSprintControl`, then the `.page-nav` row (one step Back on the left, `StageNav`'s next-stage control on the right) — because a per-page copy sits below `if (loading) …` and disappears exactly when the user is stuck. A blocked stage renders as a real disabled `<button>` (or a dimmed crumb) carrying its reason, never as a missing control. Every modal goes through `ModalShell` (Escape, focus trap, focus restore, `aria-labelledby`, overlay dismiss, and a `busy` flag that blocks both dismissal paths); every loading/error/empty state goes through `PageState`.

### Key flows

**Repo registration** (`POST /api/repos`) — validate URL → fetch metadata (verifies accessibility) → Fernet-encrypt the optional token → persist. Deactivation is a soft delete that clears the token, blocked while active sprints reference the repo.

**Sprint creation** (`POST /api/sprints`) — refresh repo metadata → best-effort `Repo.file_tree` capture (failures log, never block) → resolve README (user upload beats GitHub download; 422 if neither) → unique directory under `STORAGE_LOCATION` → persist. `CreateSprintPage` supports inline repo creation and shows README status before submit.

**Requirement analysis** (`POST /sprints/{id}/requirements`, `.../from-prd`, `tasks/analyze_requirement.py`)
Rows are created `pending` and enqueued best-effort, one RQ job each (arg = requirement id only). PRD upload (`.md`/`.markdown`/`.txt`/`.pdf`/`.docx`, capped at `PRD_MAX_CHARS`) splits **synchronously** via `llm.split_prd`; rows are marked `from_prd=True` and a re-upload replaces the previous upload's rows in one transaction, leaving manual rows alone.
Lifecycle `pending → analyzing → needs_clarification ⇄ analyzing → ready → confirmed`, plus `failed` + Restart. Clarification capped at `MAX_CLARIFICATION_ROUNDS`; confirm per-row or via `confirm-all` (one set-based UPDATE, ineligible rows silently skipped).
`confirmed` is **not** terminal — edit and delete stay open and fire the cascade (see Post-confirmation editing). Frontend polls every 2.5 s while rows are in progress; prompts carry README + file tree.

**Test environment access** (`/sprints/:id/test-environment`, `routes/test_environment.py`)
Gate: ≥1 requirement, all `confirmed` (`Sprint.requirements_complete`). The sufficiency check is **synchronous** inside the request (`asyncio.to_thread`, no queue/worker); `LLMError` → 502 and nothing persists. One row per sprint; lifecycle `needs_info ⇄ ready → confirmed`, answer/rewrite loop capped at `MAX_TEST_ENV_REVISION_ROUNDS`, direct edit + resubmit uncapped.
On every `sufficient` verdict a second call (`llm.generate_env_vars`) extracts `{"NAME": "value"}` into `env_vars_json` — **skipped when the resubmitted text is byte-identical** (`_resolve_env_vars_json`, see Gotchas), cleared to `None` if a later check comes back insufficient. The variables are directly editable via `PATCH /test-environment/{id}/env-vars` before confirming (uncapped, no LLM call).
Confirm is manual and 422s on `requirements_stale` (the UI offers Re-check) or a missing `env_vars_json`.

**Test planning** (`/sprints/:id/test-plans`, `routes/test_plans.py`, `tasks/generate_test_plan.py`)
Gate: `environment_confirmed`. Generate creates one `TestPlan` per confirmed requirement + one RQ job each — idempotent: existing plans skipped, `failed` plans reset. Lifecycle `pending → generating → draft ⇄ generating → approved`, plus `failed` + Restart.
One LLM call, **deliberately code-blind** — no `read_file`, and the parameter is absent from the signature rather than passed `None` (see Gotchas). `TEST_PLAN_BAR` demands script-checkable `expected_result`, environment-seedable preconditions, and repeatable cases. Plans store complexity + summary + `TestCase` rows; revisions **archive** the outgoing cases rather than deleting them.
Feedback capped at `MAX_TEST_PLAN_FEEDBACK_ROUNDS` (`feedback_cap_reached`); direct edit is uncapped, never touches `revision_count`, stays `draft`. Approve per-plan or via `approve-all`. Approval gates **running**, not editing — an edit returns an approved plan to `draft`.

**Test execution** (`/sprints/:id/test-runs`, `routes/test_execution.py`, `tasks/execute_test.py`)
Gate: every selected requirement has an `approved` plan. Run creation refreshes README/file tree from GitHub **once for the whole run** (skipping the README when `readme_user_provided`), then creates one `TestRun`, one `TestExecution` per requirement, and one `TestCaseExecution` per plan case seeded `pending`.
Per case: reuse `TestCase.script` if cached, else `llm.generate_test_script` — a bounded `read_file` loop (`TEST_EXECUTION_TOOL_ROUNDS`), the **only** stage with repo access — then `run_script` with the confirmed env vars injected. On failure `llm.diagnose_and_fix_script` classifies `script_bug` (apply fix, retry up to `MAX_SCRIPT_FIX_ROUNDS`) or `app_bug` (stop immediately).
Outcomes: `passed`, `failed` (app bug — script cached), `error` (self-heal exhausted — cache untouched), `skipped` (stamped by `finalization.py`, never by the loop). Both failure outcomes record a structured finding — `failed` → `bug`, `error` → `issue` — and the `app_bug` report costs **no extra LLM call** (the diagnosis returns it).
`script_snapshot` downloads via `GET /test-case-executions/{id}/script`, credential-free by construction (scripts only read `os.environ`). Restart is uncapped; the frontend polls every 2.5 s.

**Exploratory testing** (`/sprints/:id/test-runs`, `routes/exploratory.py`, `tasks/explore_requirement.py`)
Same gate as scripted runs, shown as a second list on the same page. Organized with **SBTM** (charter-driven, time-boxed sessions each producing a session sheet) and **SFDIPOT** (product-elements heuristic). Scope is **one requirement** per run.
`POST /sprints/{id}/exploratory-charters/generate` drafts charters synchronously and nominates `base_url_env_vars`, validated against the real env vars — every name must exist and hold an `http(s)` URL. **Order matters**: each session opens on the first URL. The user edits the charters, then `POST /sprints/{id}/exploratory-runs` re-validates everything (charters are user input now → 422) and creates one `ExploratoryRun` + one `ExploratorySession` per charter, enqueued as a **single** RQ job. The schema is one level shallower than the scripted side — `ExploratoryRun` fuses `TestRun`'s list identity with `TestExecution`'s job machinery.
Charters run **sequentially**, each with a live `BrowserSession` and a bounded tool loop (`llm.run_exploration_loop`). Tools: `snapshot`, `navigate`, `click`, `fill`, `fill_secret`, `press`, `go_back`/`go_forward`, `set_viewport`, `read_console`, `record_finding`, `finish_session` — every executor returns a string and never raises. Typed navigation is origin-locked (re-checked after the navigation settles); link-driven off-origin navigation is allowed and flagged by a notice on every snapshot.
Context is bounded mechanically (`EXPLORATORY_SNAPSHOT_WINDOW` verbatim snapshots, older ones become placeholders), with LLM compaction as a pressure-triggered backstop at `EXPLORATORY_CONTEXT_TOKEN_LIMIT`. Sessions end on `finish_session` or the `EXPLORATORY_MAX_ACTIONS` cap (forced wrap-up); a session that raises is marked `error` and the run continues.
Findings are written live by `record_finding` with a screenshot and `browser_environment()`. After every charter one best-effort call writes the run `summary` (recoverable via `POST /exploratory-runs/{id}/summarize`). Restart is uncapped and skips completed sessions.

**Issue-tracker integration** (`routes/issue_tracker.py`, `services/issue_tracker.py`, `services/finding_export.py`)
One `IssueTrackerConfig` per sprint — a **Jira project** or a **GitHub Issues repo**, never both. Only **bug** findings file. Credentials are Fernet-encrypted and **verified against the live tracker on every save** (`TrackerError` → 422, `TrackerUnavailableError` → 502); nothing persists unless verification succeeds, and there is deliberately no background re-verification.
GitHub connections can use the sprint's own repository (`use_sprint_repo`): `owner/repo` derives from `Repo.github_link` and a blank token falls back to `Repo.github_token` — a **copy taken at save time**. `_resolve_token` order: typed → repo's → stored same-provider → 422; a token is required when the provider changes.
Export runs at exactly two automatic call sites (each task's post-`COMPLETED` commit, outside the `try`) plus the two retry routes. The rule: **a run that finished reports its bugs; anything else waits for a human.** The run's `export_findings` toggle governs only the automatic half — the retry routes pass `requested=True`.
De-duplication is one indexed lookup: the defect's `DefectGroupTicket` row for the current `tracker_target`. A match is adopted only if `issue_is_open`; a closed ticket gets a fresh one carrying a back-reference. Per group the representative and its duplicates share the key/url, committed per group. Redaction happens inside `create_issue` — env-var values minus the base URLs, substring-matched, bounded by `_MIN_REDACTABLE_LENGTH`.

**Defect grouping** (`services/finding_grouping.py`, `DefectGroup`, `DefectGroupTicket`)
`assign_defect_groups` runs at the same two automatic call sites as export, immediately **before** it (load-bearing ordering), plus once inside `_export` — so grouping still happens with no tracker connected. Mechanically it is `finding_dedup`'s prefilter-then-one-LLM-pass, matched against stored `DefectGroup` rows.
The pass is **append-only**: a finding joins a group or opens one, and a group's text is frozen at creation; severity is derived as the max over members, never stored. It filters to `BUG` itself, skips rows that already carry a group (idempotent across restarts), and takes `SELECT … FOR UPDATE` on the sprint row before reading known defects, since concurrent sibling jobs would otherwise read stale lists. Never raises; rolls back on failure.
`UNIQUE (defect_group_id, tracker_target)` states the invariant: one defect gets at most one ticket per tracker. Expect `bug_count` to be **monotonic within a sprint** — it reports what testing found, not what is currently open.

**QA metrics** (`services/qa_metrics.py`, `GET /api/sprints/{id}/qa-metrics`, `SprintMetricsPanel`)
A panel above both run lists: how much was tested, how many distinct defects, two densities, a per-requirement breakdown. Pure read, no LLM call, both relationship chains `selectinload`ed, never raises (the page polls it every 2.5 s).
Three counting rules: **only `completed` runs count** (excluded ones are named, not dropped); **scripted cases are counted at two levels that never mix** — `distinct_test_cases_run` is the density denominator, `case_executions` describes volume; **one bug is one defect**, keyed `("group", …)` → `("ticket", …)` → `("text", …)` in that order. Exploratory sessions stay cumulative and are never summed with scripted counts; issue findings are never collapsed.
`bugs_per_requirement` divides by `requirements_covered`, not `requirements_total` (display-only, and it can legitimately read lower). Both densities are `float | None`, null when the denominator is zero. Per-requirement rows may legitimately sum **above** the headline, since grouping is sprint-scoped.

**CI/CD export** (`routes/cicd.py`, `tasks/export_cicd.py`, `services/cicd_*.py`)
A sprint's cached Playwright scripts become a **pull request** against the sprint's own
repository: our verified scripts committed verbatim under `qa-agent-tests/`, plus CI files an LLM
authors by reading the repo's existing conventions. The PR _is_ the deliverable — nothing here
ever merges it, and that human review is the gate that catches a generated workflow being wrong in
a way no check of ours could.
One `CicdConfig` per sprint (provider + Fernet-encrypted write token), verified against the live
repository on **every** save by `check_write_access` — a stronger claim than the tracker's "can I
file here", checked at save time so a read-only token is refused before an LLM call is spent. It
asks **two** questions, because they have two answers: `permissions.push` (the account's role) and
`X-OAuth-Scopes` (the credential's grant) — see Gotchas.
A case is exportable when it has a cached script whose three `script_*_revision` stamps still
match the sprint; staleness is decided by the **same** `outdated_reasons` the run badges use. NULL
revisions read as stale (unknowable ≡ stale — they share one remedy). Ineligible cases are listed
with their reason, never hidden.
The job: refresh metadata → re-derive eligibility → fetch existing CI → **one** LLM call
(`generate_cicd_integration`, bounded `read_file` loop) → `validate` → splice → write. The write
sequence is **4 requests regardless of case count** (file content rides inline in the tree
request), over one shared client. `CicdExportItem` rows are receipts written _only_ after the
commit succeeds; `selected_case_ids_json` is what the user asked for and is what the job reads.
The model authors a **job or stage body**, never a whole file — the splice is ours (`add_job` /
`insert_stage`), so a truncating rewrite of the team's CI is not expressible in the schema. There
is likewise no field that could carry a test script, the path allowlist excludes `qa-agent-tests/`
outright, and the commit applies our scripts **last** — three layers, because "the LLM never edits
a verified script" held in the schema while a `files` entry aimed at a script's path did not.
`validate` refuses a host edit outside `host_candidates` (D34 is gated, not merely prompted): a job
inherits its workflow's triggers, so attaching the suite to an `on: pull_request` host would run it
against a live environment on every PR in a repo we do not own.
The PR text is split the same way as everything else here: the title is the model's verbatim, the
body is its prose plus a deterministic trailer (`cicd_export.pr_body`) — case inventory, the
variables and secrets to create (names only), notes, dropped paths. Rule 6 of the prompt forbids
the model restating any of it, because two setup checklists that disagree are worse than one.
Env var names reach CI through `cicd_export.reference_map` — **one derivation**, read by the block,
the prompt, the trailer and the gate alike, and the one place a many-to-one sanitizer's collisions
are separated. The variable/secret split is
`environment_utils.variable_and_secret_names`, over `ci_variable_values` rather than `url_values`
(see Gotchas for why those are different questions). Both providers bind the same direction: CI
supplies the mapped name, the script reads the sprint's own. Jenkins uses `withEnv`, not
`environment { }`, which cannot carry a name that is not a Groovy identifier.
Restart is uncapped and every attempt writes a **fresh branch**, which is what makes a retry
idempotent. A finished sprint may still export (see `inactive_sprint_ok`).

**Post-confirmation editing** (`services/invalidation.py`)
One module owns what an edit invalidates, because four callers need the identical answer (requirement edit, add, delete, PRD bulk replace). The rules are asymmetric: **editing** a requirement removes its plan and un-confirms the environment; **adding** un-confirms the environment only; **deleting** removes only its own plan. An **environment** change removes every plan in the sprint; a **plan** edit returns it to `draft`.
Removing a plan archives and **detaches** its cases (`test_plan_id = None`) and deletes the plan row. Nothing regenerates automatically — `Sprint.test_plans_missing` is what lets the page offer "Generate missing test plans" exactly when pressing it would do something.
**Edits are never blocked on work in flight.** The workers stop themselves instead: `execute_test` between cases and `explore_requirement` between charters check `outdated` and bail with `SUPERSEDED_ERROR`.

**Run staleness** (`models/database.py::outdated_reasons`)
A run records the three `content_revision` values it executed against (`requirement_revision` / `plan_revision` / `env_revision`); an inequality later means it no longer describes the current sprint. Revisions, not timestamps — `updated_at` is stamped by confirm/approve/restart, none of which change what a run was testing.
Deletion is the limit case: an archived requirement yields the `requirement` reason, so `outdated == bool(outdated_reasons)` holds everywhere. A missing plan counts as outdated; a missing environment row does not. `outdated` is **not serialized** — the frontend derives it in `src/outdated.ts`. Restart is refused on any outdated run; the remedy is a new run.

**Terminal parents leave no non-terminal children** (`services/finalization.py`)
`TestCaseExecution` and `ExploratorySession` have exactly one writer each — their task's loop — so anything that ends the parent early strands them. `abandon_unreached_children` marks every non-terminal child `skipped` and stages without committing, reached from `finalization.fail_row` / `record_failure` (which the tasks call), `finish_sprint`, and the reconciler's failing branches — all through the `child_spec` on `RowSpec` or `SweepSpec`. It is deliberately **not** called on branches that re-queue the parent — a `running` child there is what the next attempt resumes from — and `skipped` is not in either task's finalized set, so a restart re-runs those children.

## Authentication

Shared-secret password gate backed by an HttpOnly session cookie; fully open when `APP_PASSWORD` is unset.

- `utils/auth.py::verify_auth` reads the `qa_auth` cookie and compares with `secrets.compare_digest()`, raising 401 on mismatch.
- Open: `/api/health`, `POST /api/auth/verify` (sets the cookie), `GET /api/auth/check` (never 401s). Every other router declares `dependencies=[Depends(verify_auth)]`.
- Cookie: `qa_auth=<password>; Path=/; SameSite=Strict; HttpOnly` (session-scoped).
- `AuthContext` runs `checking` → `authenticated`/`unauthenticated` on mount; the browser sends the cookie automatically, so API functions need no auth handling.

## Testing

### Backend (`backend/tests/`, pytest)

- `conftest.py` has an **autouse fixture that replaces the PostgreSQL engine with in-memory SQLite** and no-ops `init_db` — no test touches a real database. It also sets a fresh `ENCRYPTION_KEY`, disables dotenv, and deletes `SSL_CERT_FILE` (a Windows footgun that breaks httpx client creation).
- A second autouse fixture (`_isolate_redis`) no-ops `QueueService._connect`, so no test can enqueue to live Redis. Tests asserting enqueue behaviour monkeypatch `get_queue_service` with a recording stub.
- `async_client`: httpx `AsyncClient` over `ASGITransport` with auth disabled, Redis health mocked, `get_session` overridden, and storage pointed at `tmp_path`.
- GitHub calls are mocked with **pytest-httpx**; use the shared `_create_repo(client, url, httpx_mock)` helper to seed repos through the API.
- LLM calls never hit the network: `test_llm.py` stubs `_get_client`; task/route tests monkeypatch `services.llm` functions. Tasks and the reconciler are tested as plain functions against the SQLite fixture.
- Exploratory runs never launch a real browser (`services.browser_session.BrowserSession` is monkeypatched; `test_browser_session.py` mocks Playwright itself). Test execution never runs a real subprocess except in `test_script_runner.py`, which uses plain Python scripts only. **The browser and subprocess layers' real correctness can only be established by manual e2e.**
- Tracker calls never reach the network: `test_issue_tracker.py` drives the transport against pytest-httpx; everything above it monkeypatches `services.issue_tracker` / `services.finding_export`.
- The reconciler loop starts via FastAPI lifespan, which `ASGITransport` never runs — it is inert in API tests; `reconcile_once` is unit-tested directly.

### Frontend (Vitest + Testing Library)

- Config lives in `vite.config.ts` under `test` (jsdom, `globals: true`). Tests are colocated with source.
- `src/test/test-utils.tsx` exports `renderWithRouter(ui, { initialEntries? })`.
- Mock the API module (`vi.mock('../services/api')`) rather than raw `fetch`; mock `useNavigate` to assert navigation.
- Polling tests: install `vi.useFakeTimers()` **before** rendering — an interval registered under real timers can't be advanced later.

| **The name a CI system carries is derived in exactly one place**                       | `cicd_export.reference_map` — read by the deterministic block, the prompt, the PR trailer and the validation gate. When each derived its own, they disagreed: the block emitted `${{ vars.BASE_URL }}` for a sprint variable called `base_url` while the gate was handed `base_url`, so the gate refused our own output. **No retry can fix that class of bug** — every attempt regenerates the same text — and it fired for any name the CI system will not take verbatim, which is precisely what the sanitizers exist for. Three sanitizers, not two: Actions names, Jenkins credential ids, and Jenkins env names are three namespaces. Every sanitizer is also **many-to-one** — `base_url` and `base.url` both become `BASE_URL` — and that collision is invisible everywhere else: the block emits one reference for two variables and the gate accepts a name it supplied itself, so the export succeeds with one script reading the other's value. `reference_map` separates them with a numeric suffix, **within a namespace only** (`vars.X` and `secrets.X` are different stores, so suffixing one invents a difference CI does not have), and sorts by name rather than following `env_vars_json` — whose order an edit can change, which would silently re-point variables the team already created. ## Redis / RQ

- **Windows has no `os.fork()`**: `worker.py` uses `SimpleWorker` on win32, and RQ's `job_timeout` hard-kill is a Linux-side backstop only — on Windows the long wait is the LLM call, bounded by `OPENAI_TIMEOUT`. Crashed or hung workers are caught by the DB heartbeat + reconciler instead.
- **One `QueueService` per process**: lazy module-level singleton, never constructed per-request. Degrades gracefully when Redis is down — rows stay `pending` and the reconciler enqueues them on recovery.
- **Tasks are enqueued by dotted string path**, so the web process never imports task modules. Task modules must not import `backend.services.queue` or `backend.worker` (circular-import rule).
- **Redis is transport only**: PostgreSQL carries the whole lifecycle, which makes every enqueue idempotent (tasks no-op on rows that aren't `pending`/`analyzing`).
- The deployment runs **several workers**, and a `TestRun` fans out into a job per `TestExecution` — sibling jobs routinely finish together.

## CI/CD and Quality Gates

Both workflows trigger on `pull_request` to **`main`**: `backend_ci.yml` (Python 3.12 → `pip install -e ".[dev]"` → `pytest`; no lint step) and `frontend_ci.yml` (Node 22 → lockfile sync → `npm ci` → lint → build → test).

Pre-commit runs Ruff (lint + format), Prettier + ESLint, and general hooks (trailing whitespace, EOF, YAML/TOML, 500KB file cap, merge conflicts, private keys). Do not skip hooks unless explicitly asked. Scope manual runs to `git diff --name-only`, not `--all-files` (EOL churn).

## Conventions and Notes

1. **Working directory**: repo root for backend commands; `cd frontend` for frontend commands.
2. **Python imports** are `backend.`-prefixed; always run modules as `python -m backend.main` from the repo root.
3. **Planning docs** live in `thoughts/plans/`, implementation tracking in `thoughts/implementations/` (git-ignored).
4. **Response types**: every endpoint declares a `response_model` from `models/types.py`; table models stay in `models/database.py`.
5. **Error handling**: raise `HTTPException` with a helpful `detail`; the global handler catches the rest as a 500. GitHub failures map to 422 (validation-time) or 502 (fetch-time).
6. **Frontend error parsing**: FastAPI `detail` can be a string or `[{ msg }]` — route all fetches through `handleResponse` in `services/api.ts`.
7. **Ports**: backend 8000, frontend 5173.
8. **Commit messages / PR descriptions**: do not mention that they were written by Claude.
9. **Bulk row updates**: prefer one set-based `update()` over a load-and-mutate loop. The per-row loops in `finish_sprint` and the reconciler sweeps are deliberate exceptions (expected N ≈ 0, per-row logging) — don't copy that pattern where the row count can grow.
10. **Config-derived UI decisions**: never duplicate a backend config constant as a frontend literal — expose a computed flag on the response model instead (`clarification_cap_reached`, `feedback_cap_reached`, `Sprint.test_plans_missing`, and the rest of the `SprintResponse` flags).
11. **Database migrations**: every change to an existing table needs an idempotent migration appended to `_MIGRATIONS` in `backend/migrations.py`, using `sqlalchemy.inspect()` to check before altering and avoiding DDL SQLite lacks. `create_all` only creates missing tables.
12. **README docs stay current**: any change to user-facing behavior, setup, commands, config, or the API surface updates `README.md`, `backend/README.md` and `frontend/README.md` alongside this file.
13. **A style shared by two pages belongs in `styles/controls.css`**: colocated `.css` files hold only selectors prefixed with their own page or component (`.test-runs-section`, `.requirement-card-actions`). Anything unprefixed — `.btn*`, `.badge*`, `.run-badge*`, `.session-badge*`, `.page-nav`, `.cascade-notice` — goes in `frontend/src/styles/controls.css`, imported once from `App.tsx`. Putting a global class in a page's own file appears to work, because nothing is code-split and every stylesheet is always loaded, but it fails two ways and both had already happened here: two pages defined `.run-badge-pending` in different colours and import order silently picked the winner; and `ExploratorySessionPage` rendered `.session-badge`, styled only by a file it never imports — which would break the day someone adds `React.lazy`.
14. **Colours are tokens, and dark mode is part of the change**: no literal colour belongs anywhere but `index.css`, and every token added to `:root` gets a counterpart in the `prefers-color-scheme: dark` block — including a **foreground** for anything with its own background, since `--accent` inverts between schemes and a hardcoded `#fff` label lands at ~2:1 in dark mode. A token defined as `var(--other)` needs no dark override; custom properties substitute at computed-value time. Status colour belongs to the one shared scale (`--status-*`), so a state that means the same thing on a requirement, a plan, an environment and a run looks the same in all four — a mechanical token swap that keeps the old colour is not the fix.
15. **One definition per pipeline stage**: a stage's label, route pattern, gate and blocking reason live once in `frontend/src/stages.ts`, read by the route table's crumbs, the breadcrumb's forward crumbs and `StageNav` alike. Two chrome elements describing the same gate must not be able to disagree about whether it is open or why it is shut. Gates read `SprintResponse` flags (Convention #10), never a re-derivation from the rows on screen — a requirement with no plan contributes no row, so counting what is rendered reports "all approved" for a sprint that is not. And a mutation that can move a gate must re-read the sprint: resubmitting a confirmed environment deletes every plan in the sprint, and without the refetch the control still points at the page whose contents just went away.
