# CLAUDE.md

## Project Overview

QA Agent is a full-stack application for managing QA analysis of GitHub repositories. Users register GitHub repos, then create **sprints** linked to a repo. Creating a sprint downloads the repo's README (or accepts a user-uploaded one) plus a filtered file-tree listing and stores them for analysis. Within a sprint, users enter **requirements** — typed into a form or extracted from an uploaded **PRD document** that an LLM splits into requirements — which an LLM checks for QA-clarity via Redis/RQ background workers, with a clarification question/answer loop per requirement (see [Requirement analysis](#key-flows)). Once every requirement is confirmed, the user describes **test environment access** in free text, judged synchronously by the LLM, which also extracts the access details (URLs, credentials) into structured, editable environment variables; confirming it locks the sprint's requirement set (see [Test environment access](#key-flows)). Next, the user generates a **test plan** per requirement — an RQ worker runs an LLM tool loop that reads repository files to ground the test cases, and each draft plan goes through a capped feedback loop or uncapped direct edit until approved (see [Test planning](#key-flows)). Finally, the user runs the approved test plans — an RQ worker generates (or reuses) a Playwright script per test case, executes it in a subprocess with the confirmed environment variables injected, and self-heals script bugs via an LLM diagnosis loop, stopping and reporting a `failed` case as soon as the failure looks like a genuine application bug (see [Test execution](#key-flows)). It consists of a FastAPI + PostgreSQL backend and a React + Vite frontend.

**Prerequisites for running the backend:** PostgreSQL running with a `qa_agent` database (`createdb qa_agent`), and `backend/.env` present (copy from `backend/.env.example`). Tables are auto-created on startup by `init_db()`; changes to existing tables ship as idempotent migrations run at startup (see Conventions #11). Requirement analysis, test-plan generation, and test execution additionally need Redis, a worker (`python -m backend.worker`, second terminal), and an LLM API key (`OPENAI_API_KEY`); without them the rows simply stay `pending`. Test execution's worker host additionally needs `playwright install chromium` run once (`pip install -e ".[dev]"` installs the `playwright` package itself, but not the browser binary). Tests need none of these (see [Testing](#testing)).

### Key flows

**Repo registration** (`POST /api/repos`): validate GitHub URL → fetch metadata from GitHub API (verifies accessibility) → encrypt optional access token with Fernet → persist. Deactivation is a soft delete that clears the token and is blocked while active sprints reference the repo.

**Sprint creation** (`POST /api/sprints`): validate name + repo → refresh repo metadata from GitHub → best-effort file-tree capture onto `Repo.file_tree` (filtered + size-capped; failures log a warning, never block) → resolve README (user upload wins over GitHub download; 422 if neither) → generate unique directory under `STORAGE_LOCATION` → save README if `STORE_OFFLINE=true` → persist sprint. Frontend `CreateSprintPage` supports inline repo creation, shows README status before submitting, and navigates to `/sprints/:id` on success.

**Requirement analysis** (`POST /api/sprints/{id}/requirements` + worker): rows are created `pending` and enqueued best-effort (one RQ job per requirement, arg = requirement id only). Alternatively, `POST /api/sprints/{id}/requirements/from-prd` accepts a PRD upload (`.md`/`.markdown`/`.txt`/`.pdf`/`.docx`; text extracted via `utils/prd_utils.py`, capped at `PRD_MAX_CHARS`) and splits it into requirements with a **synchronous** LLM call (`llm.split_prd` via `asyncio.to_thread`, like the test-environment check; `LLMError` → 502, zero/too-many requirements → 422 — all before anything is persisted). The split rows are marked `from_prd=True` and a re-upload **replaces** the previous upload's rows in the same transaction (manual rows untouched; UI confirms first); the original file is stored best-effort as `PRD<ext>` when `STORE_OFFLINE=true`. From there PRD rows are ordinary requirements. The worker task is state-driven: initial clarity check, or — when `clarifying_question` + `pending_answer` are set — a revision that rewrites the description. Lifecycle: `pending → analyzing → needs_clarification ⇄ analyzing → ready → confirmed`, plus `failed` with a Restart action. PostgreSQL is the sole status of record (Redis is transport only); the frontend polls `GET /api/sprints/{id}/requirements` every 2.5 s while rows are in progress. Clarification is capped at `MAX_CLARIFICATION_ROUNDS` (3); past the cap only confirm-as-is or manual edit. `confirmed` is content-terminal (all mutations 422) but rows can still be deleted — in any status, until the test environment is confirmed (then create/delete 422 too — see below). Finishing a sprint marks its `pending`/`analyzing` requirements `failed` (nothing analyzes on a finished sprint; as backstops, the worker task fails rows whose sprint went inactive, and the reconciler fails any in-progress rows it finds on inactive sprints). The reconciler (asyncio task in the app lifespan) re-enqueues `pending` backlog when Redis recovers and sweeps `analyzing` rows with stale `last_heartbeat` (crashed worker) back to `pending`, marking them `failed` after `MAX_AUTO_RETRIES`; its database sweeps run even while Redis is down. LLM prompts include the sprint README (stored copy → re-download → none) and `Repo.file_tree` as context.

**Test environment access** (`/sprints/:id/test-environment` + `routes/test_environment.py`): the second sprint stage, reachable via SprintDetailPage's Continue button once ≥1 requirement exists and all are `confirmed` (`Sprint.requirements_complete`; the click handler re-fetches the sprint so the flag is fresh). The user submits a free-text access description; the route runs a **synchronous** LLM sufficiency check inside the request (`asyncio.to_thread`, up to `OPENAI_TIMEOUT` — no queue/worker/reconciler; on `LLMError` → 502 and nothing is persisted). Prompts include the confirmed requirements, README, and file tree. One row per sprint (`TestEnvironmentAccess`, unique FK). Lifecycle: `needs_info ⇄ ready → confirmed` — insufficient text yields a clarifying question, answered via an LLM rewrite loop capped at `MAX_TEST_ENV_REVISION_ROUNDS` (3); direct edit + resubmit is always available and uncapped (no confirm-as-is from `needs_info`). Whenever a submit/answer check comes back `sufficient`, a **second** synchronous LLM call (`llm.generate_env_vars`) extracts the access details (URL, credentials, …) into a structured `{"NAME": "value"}` map persisted as `TestEnvironmentAccess.env_vars_json`; it's cleared back to `None` if a later resubmission comes back insufficient, so it never describes stale content. The extracted variables are shown on the page and directly editable (uncapped, no LLM call) via `PATCH /test-environment/{id}/env-vars` any time before confirming — this is the only place literal secret values are ever handled at rest, same trust class as `content` itself. Confirm is manual and terminal; it 422s if any confirmed requirement's `updated_at` is newer than the row's (`requirements_stale` — the row's `updated_at` doubles as last-checked time; the UI offers Re-check, which re-POSTs the current content) or if `env_vars_json` is somehow still `None` (defensive guard, should be unreachable). Once confirmed, requirement create/delete 422 (`Sprint.requirements_locked`; the UI hides the form and Remove buttons). Sprint-list cards link straight to the test-environment page for active sprints with a submission. Backend-computed flags on `SprintResponse` (`requirements_complete`, `has_test_environment_submission`, `requirements_locked`, `has_test_plans`, `test_plans_complete`, `has_test_runs`) drive all frontend decisions (Convention #10).

**Test planning** (`/sprints/:id/test-plans` + `routes/test_plans.py` + worker): the third sprint stage, reachable via TestEnvironmentPage's "Continue to Test Plans" link once the test environment is `confirmed`. "Generate test plans" (`POST /api/sprints/{id}/test-plans/generate`, 422 unless `requirements_locked`) creates one `pending` `TestPlan` row per confirmed requirement and enqueues one RQ job each — idempotent: existing plans are skipped, `failed` plans are reset like Restart, and the full list is returned. The worker task (`tasks/generate_test_plan.py`) mirrors `analyze_requirement` (same machinery columns, idempotency guards, mid-flight status re-check, `_record_failure` retry/`failed` disposition) and is state-driven: `pending_feedback` set → LLM revision, else initial generation. The LLM call is a **bounded tool loop** (`services/llm.py::_complete_with_tools`, generalized over a result model + round budget): up to `TEST_PLAN_TOOL_ROUNDS` (8) rounds in which the model may call `read_file(path)` — the executor validates paths against `Repo.file_tree`, fetches via the GitHub contents API, truncates to `TEST_PLAN_FILE_MAX_CHARS`, and returns error strings (never raises) so GitHub failures never fail the job; after the cap a final `tool_choice="none"` call forces the JSON answer. Every round sends `tools` together with `response_format={"type": "json_object"}` (verified against DeepSeek — without JSON mode the final answer comes back fenced); the remaining budget is appended to each tool result so the model can pace itself; `on_round` heartbeats after every round so a live loop is never swept. Plans store complexity (`low`/`medium`/`high`, rigor scaled accordingly) + summary + `TestCase` child rows (delete-orphan cascade; revisions/edits replace cases wholesale; `steps` is newline-joined text; `TestCase.script` caches a generated test script — see below). Prompt context: requirement, sibling requirement names (scope boundaries only), README, file tree, and the confirmed test-environment content. Lifecycle: `pending → generating → draft ⇄ generating (feedback revision) → approved` (terminal), plus `failed` with Restart (keeps `pending_feedback` so an interrupted revision resumes); the frontend polls every 2.5 s while plans are in progress. Feedback is capped at `MAX_TEST_PLAN_FEEDBACK_ROUNDS` (3, exposed as `feedback_cap_reached`); direct edit (PATCH, validated field-by-field) is uncapped, never touches `revision_count`, and stays `draft`. Plan jobs use `TEST_PLAN_JOB_TIMEOUT` (900 s) instead of `JOB_TIMEOUT` — the tool loop legitimately outlives the 300 s analysis timeout. Finish-sprint sweeps `pending`/`generating` plans to `failed` (route sweep + worker guard + reconciler backstop, exactly like requirements — the reconciler sweeps are parametrized over both row types via `_SWEEP_SPECS`). Sprint-list cards deep-link to the test-plans page for active sprints with plans (unless the sprint also has test runs — see below).

**Test execution** (`/sprints/:id/test-runs` + `routes/test_execution.py` + worker): the fourth and final sprint stage, reachable via TestPlansPage's "Continue to Test Runs" link once every requirement's plan is `approved`. "Run new test" opens a modal listing requirements with an `approved` plan; submitting (`POST /api/sprints/{id}/test-runs`) creates one `TestRun` (the list-page grouping entity) and, per selected requirement, one `TestExecution` row (422 if any selection isn't a confirmed requirement with an approved plan, or already has a `pending`/`running` execution) plus one `TestCaseExecution` row per plan case (all seeded `pending` upfront, in plan-case position order) — enqueued best-effort, one RQ job per `TestExecution`. The worker task (`tasks/execute_test.py`) mirrors the other two tasks' machinery (idempotency guards, `_record_failure` retry/`failed` disposition) plus defensive guards for "plan no longer approved" and "environment variables not yet established" (both should be unreachable given the route-time checks and `confirmed` being a hard precondition). It walks each non-finalized `TestCaseExecution` in order — resumability after a crash/retry comes entirely from each case's own status, no extra state needed: reuse `TestCase.script` if cached, else generate one (`llm.generate_test_script`, same bounded `read_file` tool loop as test planning, `TEST_EXECUTION_TOOL_ROUNDS`) — the generation and diagnosis prompts advertise a curated, shared list of what's actually importable (`llm_prompts.AVAILABLE_TEST_LIBRARIES`: Playwright, requests, Faker, psycopg2, sqlite3, stdlib) so the model doesn't guess at unavailable packages, since scripts run under the exact same interpreter/venv as the worker (`sys.executable`); run it (`services/script_runner.run_script`, a subprocess with the confirmed `TestEnvironmentAccess.env_vars` injected as env vars, `SCRIPT_EXECUTION_TIMEOUT` wall clock); on failure, one LLM call (`llm.diagnose_and_fix_script`) classifies `script_bug` (apply the returned fix, retry — capped at `MAX_SCRIPT_FIX_ROUNDS` additional attempts) or `app_bug` (stop immediately). Three case outcomes: `passed` or `failed` (a genuine app bug — `TestCase.script` is cached either way, since the script itself was correct) or `error` (self-heal exhausted while still `script_bug` — cache left untouched, since the script still looks broken). Scripts are prompted to seed their own preconditions and clean up any data they create in a try/finally, so re-running a cached script doesn't pollute the environment or false-positive on a stale collision. `TestCaseExecution.script_snapshot` (the exact final script) is downloadable via `GET /test-case-executions/{id}/script` — credential-free by construction, since scripts only ever read `os.environ["NAME"]` and the one place literal secret values are handled is the test-environment stage's own extraction. A failed `TestExecution` can be restarted (uncapped); the frontend polls every 2.5 s while a run is in progress. Finish-sprint sweeps `pending`/`running` executions to `failed` (same three-way pattern as requirements/plans — `_SWEEP_SPECS`'s `clear_field` is `str | None` since `TestExecution` has no pending-input field to clear). Sprint-list cards deep-link to the test-runs page for active sprints with runs (`Sprint.has_test_runs`, beats the test-plans link).

## Configuration

All backend config is environment variables loaded via `python-dotenv` in `backend/config.py`. **`backend/.env.example` is the single source of truth for the variable list** — copy it to `backend/.env` and adjust. Highlights:

| Variable                                             | Notes                                                                                                                                                                |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                       | PostgreSQL connection string (default `postgresql://postgres:postgres@localhost:5432/qa_agent`)                                                                      |
| `ENCRYPTION_KEY`                                     | Fernet key, **required** to register repos with access tokens. Generate: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` |
| `APP_PASSWORD`                                       | Shared UI password; unset = auth disabled                                                                                                                            |
| `STORE_OFFLINE` / `STORAGE_LOCATION`                 | Persist sprint READMEs to disk when `"true"` (default `./uploads`, git-ignored)                                                                                      |
| `CORS_ORIGINS`                                       | Default `http://localhost:5173`                                                                                                                                      |
| `GITHUB_API_TIMEOUT`                                 | Seconds for GitHub API requests (default 15)                                                                                                                         |
| `REDIS_*`, `JOB_*`                                   | Redis connection + RQ job timeout/TTL for the analysis queue                                                                                                         |
| `OPENAI_API_KEY`                                     | **Required for requirement analysis and the test-environment check.** Never logged or returned in responses                                                          |
| `OPENAI_BASE_URL` / `OPENAI_MODEL`                   | Any OpenAI-compatible provider; defaults target DeepSeek (`https://api.deepseek.com`, `deepseek-v4-flash`)                                                           |
| `README_MAX_CHARS`                                   | Char cap on the README text included in LLM prompts (default 8000)                                                                                                   |
| `MAX_CLARIFICATION_ROUNDS`                           | Q&A rounds per requirement before the cap (default 3)                                                                                                                |
| `MAX_AUTO_RETRIES`                                   | Automatic retries before a requirement is marked `failed` (default 3)                                                                                                |
| `PRD_MAX_CHARS` / `MAX_PRD_REQUIREMENTS`             | Char cap on extracted PRD text (50000, reject not truncate) and max requirements per split (50)                                                                      |
| `MAX_TEST_ENV_REVISION_ROUNDS`                       | Answer/revise rounds for the test-environment text before the cap (default 3); direct edit stays uncapped                                                            |
| `MAX_TEST_PLAN_FEEDBACK_ROUNDS`                      | Feedback/revise rounds per test plan before the cap (default 3); direct edit stays uncapped                                                                          |
| `TEST_PLAN_TOOL_ROUNDS` / `TEST_PLAN_FILE_MAX_CHARS` | Max `read_file` LLM rounds per plan (8) and per-file char cap (20000) for the generation tool loop                                                                   |
| `TEST_PLAN_JOB_TIMEOUT`                              | RQ `job_timeout` for plan jobs (default 900) — must cover a worst-case tool loop, unlike `JOB_TIMEOUT`                                                               |
| `MAX_SCRIPT_FIX_ROUNDS`                              | Additional self-heal attempts per test case before a stubborn `script_bug` verdict gives up (default 3; case ends `error`, not `failed`)                             |
| `TEST_EXECUTION_TOOL_ROUNDS`                         | Max `read_file` LLM rounds per test-script generation/diagnosis call (default 5) — smaller than `TEST_PLAN_TOOL_ROUNDS` since a script targets one case              |
| `SCRIPT_EXECUTION_TIMEOUT`                           | Wall-clock timeout in seconds for one test-script subprocess run (default 60)                                                                                        |
| `TEST_EXECUTION_JOB_TIMEOUT`                         | RQ `job_timeout` for test-execution jobs (default 3600) — must cover every case in a requirement's plan, each with up to `1 + MAX_SCRIPT_FIX_ROUNDS` cycles          |
| `RECONCILER_INTERVAL` / `HEARTBEAT_STALE_SECONDS`    | Reconciler tick (30 s) and crashed-worker threshold (180 s — keep above `OPENAI_TIMEOUT`)                                                                            |

Test execution's worker host additionally needs `playwright install chromium` run once — the `playwright` pip package alone doesn't include the browser binary. Not a CI dependency: task tests mock `services.script_runner.run_script` entirely.

Frontend: `VITE_API_BASE` (in `frontend/.env`, default example `http://localhost:8000`). Vite only exposes vars prefixed `VITE_`. The dev server also proxies `/api` → `http://localhost:8000` (`vite.config.ts`) to avoid CORS locally.

## Authentication

Shared-secret password gate backed by an HttpOnly session cookie. Optional — when `APP_PASSWORD` is unset the app is fully open.

- `backend/utils/auth.py` — `verify_auth(request)` dependency: reads `qa_auth` cookie, compares via `secrets.compare_digest()`, raises 401 on mismatch, passes everything when `APP_PASSWORD` unset.
- `backend/routes/auth.py` — unauthenticated: `POST /api/auth/verify` (sets cookie on match), `GET /api/auth/check` (reports state, never 401s).
- Protected: the `/api/repos*`, `/api/sprints*`, `/api/requirements*`, test-environment (`/api/sprints/{id}/test-environment`, `/api/test-environment/*`), `/api/test-plans*`, and test-execution (`/api/sprints/{id}/test-runs`, `/api/test-runs/*`, `/api/test-executions/*`, `/api/test-case-executions/*`) routers use `dependencies=[Depends(verify_auth)]`. `/api/health` and `/api/auth/*` are open.
- Cookie: `qa_auth=<password>; Path=/; SameSite=Strict; HttpOnly` (session-scoped).
- Frontend: `AuthContext` runs `checking` → `authenticated`/`unauthenticated` on mount via `GET /api/auth/check`; `RootLayout` shows `LoginModal` until authenticated. The browser sends the cookie automatically, so API functions need no auth handling.

## Testing

### Backend (`backend/tests/`, pytest)

- `conftest.py` has an **autouse fixture that replaces the PostgreSQL engine with in-memory SQLite** (`sqlite:///file:test_db?mode=memory&cache=shared&uri=true`) and no-ops `init_db` — no test ever touches a real database. It also sets a fresh `ENCRYPTION_KEY`, disables dotenv, and deletes `SSL_CERT_FILE` (a Windows footgun that breaks httpx client creation).
- `async_client` fixture: httpx `AsyncClient` over `ASGITransport`, auth disabled (`APP_PASSWORD` deleted), Redis health check mocked, `get_session` overridden to the SQLite session.
- A second **autouse fixture (`_isolate_redis`) no-ops `QueueService._connect`** — no test can enqueue to live Redis; the degraded service returns `None` from `enqueue_analysis`. Tests that assert enqueue behaviour monkeypatch `get_queue_service` with a recording stub.
- GitHub API calls are mocked with **pytest-httpx** (`httpx_mock` fixture); `conftest.pytest_collection_modifyitems` relaxes its assert-all-consumed defaults. Use the shared `_create_repo(client, url, httpx_mock)` helper to seed repos through the API.
- LLM calls never hit the network: `test_llm.py` stubs `_get_client`; task/route tests monkeypatch `services.llm` functions. The task and reconciler are tested as plain functions against the SQLite fixture (`new_session` picks up the patched engine); intermediate statuses are seeded directly via `db_session` (see `_seed_sprint`/`_seed_requirement` in `test_requirement_routes.py`).
- Test execution never runs a real subprocess/browser in task or route tests: `services.script_runner.run_script` is monkeypatched (`test_execute_test.py`) exactly like `services.llm` functions elsewhere. `test_script_runner.py` is the one place real subprocesses run — plain Python scripts only, no Playwright/browser dependency, so it stays fast and CI-safe.
- The reconciler loop starts via FastAPI lifespan, which httpx `ASGITransport` never runs — it is inert in API tests; `reconcile_once` is unit-tested directly.
- Auth-specific tests (`test_auth_routes.py`) build their own client with `APP_PASSWORD=secret123`.

### Frontend (Vitest + Testing Library)

- Config lives in `vite.config.ts` under the `test` key (jsdom, `globals: true`, setup file imports `@testing-library/jest-dom/vitest`).
- Tests are colocated with source (`*.test.tsx` next to the component).
- `src/test/test-utils.tsx` exports `renderWithRouter(ui, { initialEntries? })` — wraps the component in `createMemoryRouter` + `RouterProvider` with a catch-all route.

## Gotchas

| Gotcha                                                                                           | Solution                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`location.state` in `useEffect` deps**                                                         | `location.state` is a new reference each render → infinite re-runs. Depend on specific properties instead.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **MemoryRouter route state format**                                                              | `initialEntries` must be `[{ pathname: '/x', state: {...} }]`, not `['/x', { state }]`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **CI `npm ci` fails on peer deps**                                                               | Lockfile `"peer": true` markers from a different npm version break `npm ci`. The CI workflow runs `npm install --package-lock-only` first to normalize.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Empty optional form fields**                                                                   | Browsers send empty strings for blank optional form fields — backend routes downgrade `""` to `None` (see `access_token` in `routes/repos.py`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Windows `SSL_CERT_FILE`**                                                                      | May point at a missing file and break httpx (any client construction, incl. the OpenAI SDK's); `github_utils.py` and `services/llm.py` use a certifi-based SSL context, and conftest deletes the var for tests. **Every future outbound HTTPS request must apply the same guard**: pass `ssl.create_default_context(cafile=certifi.where())` as the SSL/verify context instead of relying on the library default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Worker must run inside the activated conda env**                                               | `services/script_runner.py` launches test scripts via `subprocess.run([sys.executable, ...], env={**os.environ, ...})` — `sys.executable` guarantees the exact same interpreter/site-packages regardless of shell state, but PATH-dependent behavior (DLL search paths, spawning other binaries) is only as correct as whatever environment the worker process itself already has, since the child just inherits `os.environ` unchanged rather than re-deriving it. Always start `python -m backend.worker` from an activated `qa-agent` conda shell — the same underlying class of issue as the `SSL_CERT_FILE` row above.                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Sprint directory uniqueness**                                                                  | Never generate directories with check-then-create; `generate_sprint_directory` uses `os.makedirs(exist_ok=False)` in a retry loop to avoid the TOCTOU race.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Token security**                                                                               | GitHub tokens are Fernet-encrypted at rest, never returned in responses (`RepoResponse` omits the field) and never logged. Keep it that way. Deliberate exception: `TestEnvironmentAccess` content is free text that may contain test credentials — it is stored in plaintext and sent to the LLM provider by design (the UI placeholder nudges users toward vault references instead of raw secrets).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Schema changes need startup migrations**                                                       | `init_db()` (`create_all`) only creates _missing tables_ — it never alters existing ones, so new columns/indexes silently miss existing databases (e.g. the `Requirement.sprint_id` index only auto-applied to fresh DBs, and later `Requirement.from_prd` needed the same treatment). Every schema change to an existing table must ship with an idempotent migration executed at app startup (see Conventions #11). Migrations live in `backend/migrations.py` (`run_migrations()`, called right after `init_db()` in `create_app()`) — one function per migration, appended to `_MIGRATIONS`, using `sqlalchemy.inspect()` to check before altering so it's a no-op on both a fresh DB and an already-migrated one, and dialect-portable between PostgreSQL and the SQLite test engine (no `IF NOT EXISTS` DDL, which SQLite lacks for columns).                                                                                                                                                                                                                                                  |
| **Bounded file-upload reads**                                                                    | Reading an `UploadFile` fully (`.read()`) before comparing its length to `MAX_UPLOAD_SIZE_MB` materialises the whole body in memory even when it's going to be rejected. Read at most `max_bytes + 1` bytes (`file.read(max_bytes + 1)`) and reject if that exceeds the cap — memory use is then bounded regardless of the actual upload size (see `_validate_readme_file` in `routes/sprints.py` and the PRD upload route in `routes/requirements.py`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Sync parsing libraries block the event loop**                                                  | pypdf/python-docx (and any similarly blocking CPU/IO-bound parse) run synchronously; calling them directly inside an `async def` route stalls every other request for the duration. Offload with `await asyncio.to_thread(...)`, the same treatment already used for LLM calls (see `extract_prd_text` in the PRD upload route) — apply this to any future route that does non-trivial synchronous work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **redis-py `socket_timeout` assignment**                                                         | `conn.socket_timeout = X` after construction is a dead attribute write — it never reaches the connection pool. Pass `socket_timeout=` to the `redis.Redis(...)` constructor (see `QueueService._connect`; pinned by `test_socket_timeout_reaches_the_connection_pool`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **SQLModel doesn't auto-update `updated_at`**                                                    | Column defaults only fire on insert. Every mutating endpoint/task must set `updated_at` explicitly on each meaningful transition.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Optional relationship annotations**                                                            | SQLAlchemy's registry can't resolve the string form `"Model \| None"` in `Relationship(...)` annotations — use `Optional["Model"]` instead (see `Sprint.test_environment`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Asserting cross-session deletes in tests**                                                     | When a worker task deletes rows in its own session (`new_session`), `db_session.get(Model, old_id)` in the test raises `ObjectDeletedError`/`DetachedInstanceError` instead of returning `None` — the test session's identity map still holds the stale instance. Capture the id before running the task, then assert absence via a fresh `select(Model.id)` (see `test_feedback_revision_replaces_cases`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **`Test*`-named production classes**                                                             | pytest tries to collect any class whose name starts with `Test` (e.g. `TestEnvironmentAccess`, `TestEnvironmentResult`) and warns/fails on `__init__`. Set `__test__ = False` on such classes in `models/database.py` / `services/llm.py`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **SQLite recycles rowids within a test session**                                                 | Deleting rows and inserting new ones in the same SQLite connection can reuse the deleted rows' ids for the new inserts (unlike PostgreSQL). A test asserting "the old rows are gone" by checking `old_id not in current_ids` can false-positive if a new row happens to land on that id. Assert by a stable field (name, a captured pre-delete id kept as a _positive_ check for survivors) instead of id-absence (see `test_replaces_prior_prd_rows_only` in `test_prd_upload_routes.py`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Unsandboxed LLM-authored code execution**                                                      | Test scripts run as a plain subprocess (`services/script_runner.py`) with no sandboxing beyond `SCRIPT_EXECUTION_TIMEOUT`. This is an accepted risk per an explicit product decision, not an oversight — don't "fix" it by adding sandboxing without checking with the user first, and don't treat it as a bug to silently paper over.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **`TestEnvironmentAccess.env_vars_json` holds live secrets in plaintext**                        | Same trust class as `content` (already plaintext by design) — it's the structured extraction of the same access description, viewable/editable on the same authenticated page. Never log it at INFO. Downloadable **test** scripts (`TestCaseExecution.script_snapshot`) are deliberately credential-free (they only ever read `os.environ["NAME"]`) and unaffected by this.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **A grounding `read_file` tool can silently become the model's source of truth for correctness** | Giving an LLM `read_file` to ground generated output in the real repo (paths, params, response shapes) also hands it the implementation — nothing stops it from treating _that_ as "correct" instead of the requirement, especially when diagnosing a failure (`diagnose_and_fix_script` reading the handler and concluding "the script's assertion is wrong" about a test that actually caught a real app bug). This slipped past code review and the full test suite on the execute-test feature — both check structure/wiring, not whether a prompt keeps the model's judgment anchored to the requirement — and only surfaced in manual e2e. Every prompt that both hands the model `read_file` and asks it to judge correctness (`TEST_PLAN_BAR`, `TEST_SCRIPT_SYSTEM_PROMPT`, `TEST_SCRIPT_DIAGNOSIS_SYSTEM_PROMPT`) must say explicitly that reading code is for confirming interface details only — never for redefining what the expected/correct outcome is. Apply the same instruction to any future prompt with this shape (tool access to ground-truth code + a judgment call to make). |

### Redis / RQ (active — requirement analysis)

RQ workers process requirement-analysis jobs (revived from the removed word-count pipeline around commit `ab337c1`). Hard-won lessons, now applied in code:

- **Windows has no `os.fork()`**: `worker.py` uses `SimpleWorker` when `sys.platform == "win32"`. `QueueService._connect` sets a 5 s socket timeout for enqueue-side Redis calls (enqueue, ping, job lookups); RQ itself bumps the worker connection's timeout above its blocking-dequeue window on startup, so dead-connection hangs are bounded on both sides.
- **RQ's `job_timeout` hard-kill also needs fork**: it stays as a Linux-side backstop; on Windows the analysis task's only long wait is the LLM call, which `OPENAI_TIMEOUT` bounds. Crashed/hung workers are caught by the DB heartbeat + reconciler instead.
- **One `QueueService` per process**: lazy module-level singleton (`get_queue_service()` / `reset_queue_service()`), never constructed per-request. Degrades gracefully (`enqueue_analysis` returns `None`) when Redis is down — rows stay `pending` and the reconciler enqueues them on recovery.
- **Tasks are enqueued by dotted string path** (`backend.tasks.analyze_requirement.analyze_requirement_task`), so the web process never imports task modules. Task modules must not import from `backend.services.queue` or `backend.worker` (circular-import rule).
- **Redis is transport only**: no `job.meta` status; PostgreSQL rows carry the whole lifecycle, making every enqueue idempotent (the task no-ops on rows that aren't `pending`/`analyzing`).

## Conventions and Notes

1. **Working directory**: repo root for backend commands; `cd frontend` for frontend commands.
2. **Python imports**: `backend.`-prefixed (`from backend.config import ...`). Always run modules as `python -m backend.main` from the repo root, never `python backend/main.py`.
3. **Planning docs**: feature plans live in `thoughts/plans/`, implementation tracking in `thoughts/implementations/` (git-ignored).
4. **Response types**: every endpoint declares a `response_model` from `models/types.py`; table models stay in `models/database.py`.
5. **Error handling**: raise `HTTPException` with a helpful `detail`; the global handler catches everything else as a 500. GitHub failures map to 422 (validation-time) or 502 (fetch-time).
6. **Frontend error parsing**: FastAPI `detail` can be a string or `[{ msg }]` — `handleResponse` in `services/api.ts` handles both; route all fetches through it.
7. **Ports**: backend 8000, frontend 5173.
8. **Commit messages / PR descriptions**: do not mention that they were written by Claude.
9. **Bulk row updates**: prefer a single set-based `update()` statement over loading rows and mutating them in a loop. The per-row loops in `finish_sprint` and the reconciler sweeps are deliberate exceptions (expected N ≈ 0, per-row logging, Python-side staleness/retry branching) — don't copy that pattern to paths where the row count can grow.
10. **Config-derived UI decisions**: never duplicate a backend config constant as a frontend literal — expose a computed flag on the response model instead (e.g. `clarification_cap_reached` is a `Requirement` property serialized via `response_model`; the card reads the flag, not `MAX_CLARIFICATION_ROUNDS`).
11. **Database migrations**: whenever a table model changes (new/altered column, index, constraint), write an accompanying migration and wire it to run at app startup (alongside `init_db()` in the startup path). `create_all` only creates missing tables, so without a migration the change never reaches existing databases. Migrations must be idempotent — startup runs them on every boot.
12. **README docs stay current**: every feature that changes user-facing behavior, setup steps, commands, config, or the API surface must update the README docs (`README.md`, `backend/README.md`, `frontend/README.md`) alongside CLAUDE.md — not just CLAUDE.md.

## MCP Tools: code-review-graph

**IMPORTANT: This project has a knowledge graph. ALWAYS use the
code-review-graph MCP tools BEFORE using Grep/Glob/Read to explore
the codebase.** The graph is faster, cheaper (fewer tokens), and gives
you structural context (callers, dependents, test coverage) that file
scanning cannot.

### When to use graph tools FIRST

- **Exploring code**: `semantic_search_nodes` or `query_graph` instead of Grep
- **Understanding impact**: `get_impact_radius` instead of manually tracing imports

- **Architecture questions**: `get_architecture_overview` + `list_communities`

Fall back to Grep/Glob/Read **only** when the graph doesn't cover what you need.
