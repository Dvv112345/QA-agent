# CLAUDE.md

## Project Overview

QA Agent is a full-stack application for managing QA analysis of GitHub repositories. Users register GitHub repos, then create **sprints** linked to a repo. Creating a sprint downloads the repo's README (or accepts a user-uploaded one) plus a filtered file-tree listing and stores them for analysis. Within a sprint, users enter **requirements** — typed into a form or extracted from an uploaded **PRD document** that an LLM splits into requirements — which an LLM checks for QA-clarity via Redis/RQ background workers, with a clarification question/answer loop per requirement (see [Requirement analysis](#key-flows)). Once every requirement is confirmed, the user describes **test environment access** in free text, judged synchronously by the LLM, which also extracts the access details (URLs, credentials) into structured, editable environment variables; confirming it opens the test-planning stage (see [Test environment access](#key-flows)). Next, the user generates a **test plan** per requirement — an RQ worker runs one LLM call grounded in the requirement rather than the implementation (deliberately code-blind) and written for automated execution, and each draft plan goes through a capped feedback loop or uncapped direct edit until approved (see [Test planning](#key-flows)). Finally, the user runs the approved test plans — an RQ worker generates (or reuses) a Playwright script per test case, executes it in a subprocess with the confirmed environment variables injected, and self-heals script bugs via an LLM diagnosis loop, stopping as soon as the failure looks like a genuine application bug and reporting it as a structured finding — severity, reproduction steps, expected vs actual, environment — in the same shape exploratory testing produces (see [Test execution](#key-flows)). Bug findings from either testing mode can be filed to a **Jira project or GitHub Issues repo** connected to the sprint — grouped first, so one defect becomes one ticket (see [Issue-tracker integration](#key-flows)). Alongside scripted runs, the user can start **exploratory testing** for a single requirement: an LLM drives a real browser through SBTM charters generated from the SFDIPOT heuristic, recording bugs and issues with screenshots and producing a session sheet per charter plus a per-requirement summary (see [Exploratory testing](#key-flows)). It consists of a FastAPI + PostgreSQL backend and a React + Vite frontend.

All backend commands run from the repo root; frontend commands from `frontend/`.

| `pip install -e ".[dev]"`               | Install backend + dev dependencies (pytest, ruff, …)                              |

| `python -m backend.worker`              | Start an RQ worker (required for requirement analysis and test-plan generation)   |

| `npm run dev`                           | Vite dev server with HMR at http://localhost:5173                                 |
| `npm run build`                         | Type-check (`tsc -b`) and build for production                                    |
| `npm run lint`                          | ESLint                                                                            |
| `npm test` / `npm run test:watch`       | Vitest (single run / watch mode)                                                  |
| `pre-commit install`                    | Install git hooks (first time only)                                               |
| `pre-commit run --all-files`            | Run all hooks on all files                                                        |

**Prerequisites for running the backend:** PostgreSQL running with a `qa_agent` database (`createdb qa_agent`), and `backend/.env` present (copy from `backend/.env.example`). Tables are auto-created on startup by `init_db()`; changes to existing tables ship as idempotent migrations run at startup (see Conventions #11). Requirement analysis, test-plan generation, and test execution additionally need Redis, a worker (`python -m backend.worker`, second terminal), and an LLM API key (`OPENAI_API_KEY`); without them the rows simply stay `pending`. Test execution's worker host additionally needs `playwright install chromium` run once (`pip install -e ".[dev]"` installs the `playwright` package itself, but not the browser binary). Tests need none of these (see [Testing](#testing)).

### Key flows

**Repo registration** (`POST /api/repos`): validate GitHub URL → fetch metadata from GitHub API (verifies accessibility) → encrypt optional access token with Fernet → persist. Deactivation is a soft delete that clears the token and is blocked while active sprints reference the repo.

**Sprint creation** (`POST /api/sprints`): validate name + repo → refresh repo metadata from GitHub → best-effort file-tree capture onto `Repo.file_tree` (filtered + size-capped; failures log a warning, never block) → resolve README (user upload wins over GitHub download; 422 if neither) → generate unique directory under `STORAGE_LOCATION` → save README if `STORE_OFFLINE=true` → persist sprint. Frontend `CreateSprintPage` supports inline repo creation, shows README status before submitting, and navigates to `/sprints/:id` on success.

**Requirement analysis** (`POST /api/sprints/{id}/requirements` + worker): rows are created `pending` and enqueued best-effort (one RQ job per requirement, arg = requirement id only). Alternatively, `POST /api/sprints/{id}/requirements/from-prd` accepts a PRD upload (`.md`/`.markdown`/`.txt`/`.pdf`/`.docx`; text extracted via `utils/prd_utils.py`, capped at `PRD_MAX_CHARS`) and splits it into requirements with a **synchronous** LLM call (`llm.split_prd` via `asyncio.to_thread`, like the test-environment check; `LLMError` → 502, zero/too-many requirements → 422 — all before anything is persisted). The split rows are marked `from_prd=True` and a re-upload **replaces** the previous upload's rows in the same transaction (manual rows untouched; UI confirms first); the original file is stored best-effort as `PRD<ext>` when `STORE_OFFLINE=true`. From there PRD rows are ordinary requirements. The worker task is state-driven: initial clarity check, or — when `clarifying_question` + `pending_answer` are set — a revision that rewrites the description. Lifecycle: `pending → analyzing → needs_clarification ⇄ analyzing → ready → confirmed`, plus `failed` with a Restart action. PostgreSQL is the sole status of record (Redis is transport only); the frontend polls `GET /api/sprints/{id}/requirements` every 2.5 s while rows are in progress. Clarification is capped at `MAX_CLARIFICATION_ROUNDS` (3); past the cap only confirm-as-is or manual edit. Confirming is available per-row (`POST /requirements/{id}/confirm`) or in bulk via `POST /sprints/{id}/requirements/confirm-all`, which confirms every currently `ready`/`needs_clarification` row in one set-based `UPDATE` and returns the full sprint list; ineligible rows (still analyzing, already confirmed, failed) are silently skipped, and the frontend's "Confirm all" button stays disabled while any requirement is still `pending`/`analyzing` so a partial batch can't be confirmed mid-analysis. `confirmed` is no longer terminal: the description can still be edited (which fires the cascade below), and rows can be deleted in any status, before or after the environment is confirmed. Finishing a sprint marks its `pending`/`analyzing` requirements `failed` (nothing analyzes on a finished sprint; as backstops, the worker task fails rows whose sprint went inactive, and the reconciler fails any in-progress rows it finds on inactive sprints). The reconciler (asyncio task in the app lifespan) re-enqueues `pending` backlog when Redis recovers and sweeps `analyzing` rows with stale `last_heartbeat` (crashed worker) back to `pending`, marking them `failed` after `MAX_AUTO_RETRIES`; its database sweeps run even while Redis is down. LLM prompts include the sprint README (stored copy → re-download → none) and `Repo.file_tree` as context.

**Test environment access** (`/sprints/:id/test-environment` + `routes/test_environment.py`): the second sprint stage, reachable via SprintDetailPage's Continue button once ≥1 requirement exists and all are `confirmed` (`Sprint.requirements_complete`; the click handler re-fetches the sprint so the flag is fresh). The user submits a free-text access description; the route runs a **synchronous** LLM sufficiency check inside the request (`asyncio.to_thread`, up to `OPENAI_TIMEOUT` — no queue/worker/reconciler; on `LLMError` → 502 and nothing is persisted). Prompts include the confirmed requirements, README, and file tree. One row per sprint (`TestEnvironmentAccess`, unique FK). Lifecycle: `needs_info ⇄ ready → confirmed` — insufficient text yields a clarifying question, answered via an LLM rewrite loop capped at `MAX_TEST_ENV_REVISION_ROUNDS` (3); direct edit + resubmit is always available and uncapped (no confirm-as-is from `needs_info`). Whenever a submit/answer check comes back `sufficient`, a **second** synchronous LLM call (`llm.generate_env_vars`) extracts the access details (URL, credentials, …) into a structured `{"NAME": "value"}` map persisted as `TestEnvironmentAccess.env_vars_json`; it's cleared back to `None` if a later resubmission comes back insufficient, so it never describes stale content. That second call is **skipped when the resubmitted text is byte-identical** (`_resolve_env_vars_json`): the variables are derived from the description, so unchanged content already has its derivation stored. Re-extracting it would re-run a non-deterministic call whose drift — one renamed key, one trailing slash — reads as a content change and deletes every plan in the sprint, and would silently overwrite any hand-correction made through the direct-edit endpoint below. Comparing after the fact (`_apply_check_result`) cannot prevent either, since it only recognises sameness the model happened to produce; it stays as a backstop for the answer path, where the text really is rewritten. The extracted variables are shown on the page and directly editable (uncapped, no LLM call) via `PATCH /test-environment/{id}/env-vars` any time before confirming — this is the only place literal secret values are ever handled at rest, same trust class as `content` itself. Confirm is manual; it 422s if any confirmed requirement's `updated_at` is newer than the row's (`requirements_stale` — the row's `updated_at` doubles as last-checked time; the UI offers Re-check, which re-POSTs the current content) or if `env_vars_json` is somehow still `None` (defensive guard, should be unreachable). Confirming no longer freezes the requirement set — adding one simply sends the environment back for re-checking (see Post-confirmation editing below). Sprint-list cards link straight to the test-environment page for active sprints with a submission. Backend-computed flags on `SprintResponse` (`requirements_complete`, `has_test_environment_submission`, `environment_confirmed`, `has_test_plans`, `test_plans_missing`, `test_plans_complete`, `has_test_runs`, `has_exploratory_runs`) drive all frontend decisions (Convention #10).

**Test planning** (`/sprints/:id/test-plans` + `routes/test_plans.py` + worker): the third sprint stage, reachable via TestEnvironmentPage's "Continue to Test Plans" link once the test environment is `confirmed`. "Generate test plans" (`POST /api/sprints/{id}/test-plans/generate`, 422 unless `environment_confirmed`) creates one `pending` `TestPlan` row per confirmed requirement and enqueues one RQ job each — idempotent: existing plans are skipped, `failed` plans are reset like Restart, and the full list is returned. The worker task (`tasks/generate_test_plan.py`) mirrors `analyze_requirement` (same machinery columns, idempotency guards, mid-flight status re-check, `_record_failure` retry/`failed` disposition) and is state-driven: `pending_feedback` set → LLM revision, else initial generation. The LLM call is a **single `_complete`** — plan generation is deliberately **code-blind**. `generate_test_plan`/`revise_test_plan` take no `read_file` executor and no `on_round`, and the parameters are absent from the signatures rather than passed `None`: a plan defines what "correct" means for a requirement, so handing the model the implementation is exactly where that judgment drifts into restating what the code already does (the `read_file`-as-source-of-truth gotcha below), and accepting `None` would leave re-enabling it one argument away. Nothing is lost, because the endpoint paths and response shapes the old loop fetched are resolved again by `generate_test_script` at execution time with a larger budget and a fresher snapshot — the plan was paying the risk to carry details that get looked up anyway, while pinning approved plans to implementation the requirement never mentioned. In exchange `TEST_PLAN_BAR` states what it is planning **for**: each case becomes one Playwright script, so `expected_result` must be script-checkable (a value, message, state, status — never a subjective judgment), preconditions must be seedable from the confirmed environment (never manual setup), cases must be repeatable, and steps say _what_ to verify rather than naming endpoints or selectors. Checks no script could make are deliberately left to exploratory testing, which covers that ground. The heartbeat is a single stamp immediately before the call: one completion bounded by `OPENAI_TIMEOUT` (60) sits well inside `HEARTBEAT_STALE_SECONDS` (180), so no per-round callback is needed. Plans store complexity (`low`/`medium`/`high`, rigor scaled accordingly) + summary + `TestCase` child rows (revisions/edits _archive_ the outgoing cases rather than deleting them — the delete-orphan cascade was removed, see the Gotchas table; `steps` is newline-joined text; `TestCase.script` caches a generated test script — see below). Prompt context: requirement, sibling requirement names (scope boundaries only), README, file tree, and the confirmed test-environment content. Lifecycle: `pending → generating → draft ⇄ generating (feedback revision) → approved`, plus `failed` with Restart. Approval gates _running_, not editing: an approved plan can still be edited or given feedback, which returns it to `draft` (keeps `pending_feedback` so an interrupted revision resumes); the frontend polls every 2.5 s while plans are in progress. Feedback is capped at `MAX_TEST_PLAN_FEEDBACK_ROUNDS` (3, exposed as `feedback_cap_reached`); direct edit (PATCH, validated field-by-field) is uncapped, never touches `revision_count`, and stays `draft`. Approving is available per-plan (`POST /test-plans/{id}/approve`) or in bulk via `POST /sprints/{id}/test-plans/approve-all`, which approves every currently `draft` plan in the sprint (scoped through `Requirement` since `TestPlan` has no direct `sprint_id`) and returns the full sprint list; the frontend's "Approve all" button stays disabled while any plan is still `pending`/`generating` so a partial batch can't be approved mid-generation. Plan jobs use `TEST_PLAN_JOB_TIMEOUT` (900 s) instead of `JOB_TIMEOUT`; now that generation is one LLM call this is vestigial headroom rather than a sized budget, kept because it costs nothing. Finish-sprint sweeps `pending`/`generating` plans to `failed` (route sweep + worker guard + reconciler backstop, exactly like requirements — the reconciler sweeps are parametrized over both row types via `_SWEEP_SPECS`). Sprint-list cards deep-link to the test-plans page for active sprints with plans (unless the sprint also has test runs — see below).

**Test execution** (`/sprints/:id/test-runs` + `routes/test_execution.py` + worker): the fourth and final sprint stage, reachable via TestPlansPage's "Continue to Test Runs" link once every requirement's plan is `approved`. "Run new test" opens a modal listing requirements with an `approved` plan; submitting (`POST /api/sprints/{id}/test-runs`) first best-effort refreshes the sprint's README/file-tree context from GitHub exactly once for the whole run (`utils/readme_utils.py::resolve_readme(..., force_refresh=True)` + `refresh_file_tree`) — skipping the README refresh when `Sprint.readme_user_provided` (a user-uploaded README is authoritative and never silently overwritten), always refreshing the file tree, and never blocking run creation on a GitHub failure — then creates one `TestRun` (the list-page grouping entity) and, per selected requirement, one `TestExecution` row (422 if any selection isn't a confirmed requirement with an approved plan, or already has a `pending`/`running` execution) plus one `TestCaseExecution` row per plan case (all seeded `pending` upfront, in plan-case position order) — enqueued best-effort, one RQ job per `TestExecution`. Refreshing once at run creation (rather than per `TestExecution`, which are separate RQ jobs) keeps every case in the run grounded in the same repo snapshot. The worker task (`tasks/execute_test.py`) mirrors the other two tasks' machinery (idempotency guards, `_record_failure` retry/`failed` disposition) plus defensive guards for "plan no longer approved" and "environment variables not yet established" (both should be unreachable given the route-time checks and `confirmed` being a hard precondition). It walks each non-finalized `TestCaseExecution` in order — resumability after a crash/retry comes entirely from each case's own status, no extra state needed: reuse `TestCase.script` if cached, else generate one (`llm.generate_test_script`, a bounded `read_file` tool loop via `services/llm.py::_complete_with_tools`, `TEST_EXECUTION_TOOL_ROUNDS` — the **only** stage with repo access, since test planning is deliberately code-blind; the executor validates paths against `Repo.file_tree`, fetches via the GitHub contents API, truncates to `TEST_EXECUTION_FILE_MAX_CHARS`, and returns error strings so GitHub failures never fail the job; after the cap a final `tool_choice="none"` call forces the JSON answer, every round sends `tools` together with `response_format={"type": "json_object"}` — verified against DeepSeek, without JSON mode the final answer comes back fenced) — the generation and diagnosis prompts advertise a curated, shared list of what's actually importable (`llm_prompts.AVAILABLE_TEST_LIBRARIES`: Playwright, requests, Faker, psycopg2, sqlite3, stdlib) so the model doesn't guess at unavailable packages, since scripts run under the exact same interpreter/venv as the worker (`sys.executable`); run it (`services/script_runner.run_script`, a subprocess with the confirmed `TestEnvironmentAccess.env_vars` injected as env vars, `SCRIPT_EXECUTION_TIMEOUT` wall clock); on failure, one LLM call (`llm.diagnose_and_fix_script`) classifies `script_bug` (apply the returned fix, retry — capped at `MAX_SCRIPT_FIX_ROUNDS` additional attempts) or `app_bug` (stop immediately). Three case outcomes: `passed` or `failed` (a genuine app bug — `TestCase.script` is cached either way, since the script itself was correct) or `error` (self-heal exhausted while still `script_bug` — cache left untouched, since the script still looks broken). A fourth status, `skipped`, is the one the loop never writes: it is stamped by `services/finalization.py` on the cases an execution ended without reaching (see Terminal parents below). Both terminal failures also record a **structured finding** on the `TestCaseExecution` row (`finding_severity`/`finding_title`/`finding_steps_to_reproduce`/`finding_expected`/`finding_actual` + `environment`), in the same vocabulary an exploratory session uses: `failed` → `bug`, `error` → `issue`, which is the SBTM "product is wrong" vs "testing was obstructed" split derived from the outcome rather than stored (`TestCaseExecution.finding_type` is a property, so a restart can't leave it contradicting `status`). The bug report costs **no extra LLM call** — `diagnose_and_fix_script` already has the test case, script, and output in hand on exactly the `app_bug` path, so it returns the report alongside the classification, normalized in the task against the test case (`title` → case title, `steps` → case steps, `expected` → case `expected_result`, `actual` → the diagnosis explanation, unknown severity → `medium`). Those fallbacks are filled rather than raising because an `LLMError` here routes into `_record_failure` and retries the whole `TestExecution` — re-running every remaining case — over a formatting slip in a report whose substance already arrived in `explanation`. The `issue` report needs no LLM call at all (the last diagnosis said `script_bug`, so there is no verdict about the product to relay; severity is fixed at `medium` because an unexercised case says nothing about whether the requirement is met). Finding columns are cleared explicitly on a `passed` case, since a restarted execution reuses its `TestCaseExecution` rows and a fixed bug must stop reporting itself. `environment` (`utils/environment_utils.py::script_environment()` — worker OS, Python, Playwright version) is part of the finding rather than the case, so it is recorded on both terminal failure paths and cleared with the rest on a pass: it is only reachable through the nested `finding` response, and writing it on a passing case would store something no reader can see. Raw `output`/`error`/`script_snapshot` are untouched — the finding is the report, the output is the debugging surface, and the UI shows both (card above, output behind its existing toggle). Scripts are prompted to seed their own preconditions and clean up any data they create in a try/finally, so re-running a cached script doesn't pollute the environment or false-positive on a stale collision. `TestCaseExecution.script_snapshot` (the exact final script) is downloadable via `GET /test-case-executions/{id}/script` — credential-free by construction, since scripts only ever read `os.environ["NAME"]` and the one place literal secret values are handled is the test-environment stage's own extraction. A failed `TestExecution` can be restarted (uncapped); the frontend polls every 2.5 s while a run is in progress. Finish-sprint sweeps `pending`/`running` executions to `failed` (same three-way pattern as requirements/plans — `_SWEEP_SPECS`'s `clear_field` is `str | None` since `TestExecution` has no pending-input field to clear). Sprint-list cards deep-link to the test-runs page for active sprints with runs (`Sprint.has_test_runs`, beats the test-plans link).

**Exploratory testing** (`/sprints/:id/test-runs` + `routes/exploratory.py` + worker): the fifth sprint stage, sharing the test-runs page with scripted runs (split into two lists: "Exploratory Sessions" and "Scripted Test Runs") and the same gate — confirmed requirements, confirmed test environment, and **approved test plans**. An LLM drives a real Playwright browser against the running application, organized with **SBTM** (Session-Based Test Management: charter-driven, time-boxed sessions each producing a session sheet) and **SFDIPOT** (Rapid Software Testing's product-elements heuristic: Structure, Function, Data, Interfaces, Platform, Operations, Time). "Start exploratory testing" selects **one requirement** — unlike `RunTestModal`'s multi-select, because exploration is expensive and read rather than glanced at; that scope is what collapses the hierarchy and gives the summary an owner. `POST /sprints/{id}/exploratory-charters/generate` runs one **synchronous** LLM call (`llm.generate_charters` via `asyncio.to_thread`, `LLMError` → 502, nothing persisted) that drafts charters tagged with the SFDIPOT dimensions that actually apply (skipping the rest), is shown the requirement's approved test cases as "already covered", and **nominates a list of env vars holding application URLs** (`base_url_env_vars`) which the route then validates against the real `env_vars` — every name must exist and hold an `http(s)` URL (502 if not, since the model produced it). **Order is load-bearing**: each session's browser opens on the first URL, so the charter prompt instructs the model to list the browsable frontend first, and the charter modal names it ("Exploration starts at `APP_URL`") rather than showing an undifferentiated list — nothing can verify programmatically that the first URL really is a frontend, so the prompt plus a visible label is the whole mechanism. The route also attaches a **heuristic** cost projection (`charters × EXPLORATORY_MAX_ACTIONS × EXPLORATORY_SECONDS_PER_ACTION`); the model is deliberately never asked to estimate duration. The user edits/adds/removes charters and submits to `POST /sprints/{id}/exploratory-runs`, which re-validates everything from scratch (charters are user input now → 422; URL vars likewise → 422), best-effort refreshes README/file tree once, and creates one `ExploratoryRun` + one `ExploratorySession` per charter, enqueued as a **single** RQ job. Schema: `ExploratoryRun` → `ExploratorySession` → `ExploratoryFinding`, deliberately one level shallower than `TestRun` → `TestExecution` → `TestCaseExecution` — `ExploratoryRun` fuses `TestRun`'s list-page identity with `TestExecution`'s job machinery, legitimate precisely because the multi-requirement batching that forced them apart doesn't exist here. The worker task (`tasks/explore_requirement.py`) walks the run's charters **sequentially** (never in parallel: charters for one requirement attack the same feature by construction, so concurrent sessions collide on the same records and manufacture false findings), giving each a live `BrowserSession` and a bounded tool loop (`llm.run_exploration_loop`, a sibling of `_complete_with_tools` — it differs in termination, memory management, and output). Tools: `snapshot` (Playwright's `aria_snapshot(mode="ai")`, returning `[ref=eN]` handles), `navigate`, `click`, `fill`, `fill_secret`, `press`, `go_back`/`go_forward`, `set_viewport`, `read_console`, `record_finding`, `finish_session`. Every executor returns a string and **never raises** (the `read_file` contract, applied to a bigger surface). `BrowserSession.__enter__` opens the page on `base_urls[0]` (guarded against an empty list, and non-fatal on failure — an unreachable app is itself a finding the model should record), and `run_exploration_loop` puts those URLs in the prompt: without both, the model only ever sees env var _names_ and has to discover the app by tripping the origin lock. Two guards matter, and they are deliberately asymmetric: **typed** navigation is **origin-locked** to the nominated URLs and re-checked _after_ the navigation settles so a redirect chain can't escape, but **link-driven** navigation off-origin is _allowed_ — an OAuth hop or an external link the charter asks about is the application's own behavior, and undoing it would remove real capability and manufacture "the link is broken" findings. What that leaves is silent drift, which `_off_origin_notice()` closes by riding along on every snapshot header (and on click/press/history results) for as long as the page is off-origin. Second guard: `fill_secret(ref, env_var_name)` resolves the literal inside the executor, so credentials never enter the LLM conversation or the stored `action_log`; a literal typed through plain `fill` is redacted from the log as a backstop (exact match against the env values, minus the base URLs). Context is bounded **mechanically** on the normal path: the last `EXPLORATORY_SNAPSHOT_WINDOW` snapshots stay verbatim, older snapshot _tool results_ become one-line placeholders, and assistant messages are never pruned (the model's own commentary is the narrative thread and doubles as wrap-up material). Behind that sits a **pressure-triggered** backstop, not a scheduled one — per-step summarization was rejected as a telephone game that loses the record IDs and verbatim error text exploration depends on. When a round's reported `usage.prompt_tokens` (falling back to a chars/4 estimate) exceeds `EXPLORATORY_CONTEXT_TOKEN_LIMIT`, the middle of the conversation is replaced by one LLM-written summary; the system prompt and the charter/requirement message are never touched (they are the oracle), nor are the last `SNAPSHOT_WINDOW + 1` message groups (they hold the refs the model is about to act on). Two traps the implementation exists to avoid: the cut must land on a group boundary or orphaned `role: "tool"` messages make the provider reject the whole request, and `snapshot_indices` are absolute so they are rebuilt from the snapshot `tool_call_id`s afterwards. A failed compaction, or being over the limit with nothing left to compact, ends the session tidily via the forced wrap-up with `stop_reason` `context_limit`. Sessions end on `finish_session` or the `EXPLORATORY_MAX_ACTIONS` cap (which forces a structured wrap-up); a session that raises is marked `error` and the run **continues to the next charter**. Findings are written live by `record_finding` — the only way to capture a screenshot while the problem is on screen — typed `bug` (product is wrong) vs `issue` (testing was obstructed), the SBTM distinction. Both `finding_type` and `severity` are passed through `FindingType.normalize`/`FindingSeverity.normalize` on persist (→ `bug` / `medium`), exactly as the scripted path normalizes its own: the tool schema constrains them to enums but the model is not bound by it, and an unrecognised value would count toward `finding_count` while counting toward neither `bug_count` nor `issue_count` — a run page whose numbers don't add up — or make `high_severity_count` mean something different depending on which mode found it. `record_finding` also takes `page_still_shows_problem` (default true): when the model notices a defect only after navigating away, the capture is **skipped** rather than attaching an image of an unrelated page, since a reader treats any attached image as evidence of the defect. That parameter is deliberately named after the fact rather than the action (`screenshot: bool` would invite the model to express a preference it has no basis for) and needs no schema change — it reuses the null-`screenshot_path` path that `STORE_OFFLINE=false` already exercises. Screenshots go through `StorageService.store_screenshot` and are therefore gated on `STORE_OFFLINE`; with it off, findings simply carry none. Every finding also records an `environment` (`utils/environment_utils.py::browser_environment()`): browser name + version, the viewport **at that instant**, host OS, and the page URL — built alongside the screenshot for the same reason, since a later action silently changes both, and a defect that reproduces at 375px wide and not at 1280px is a different defect. Captured in code, never added to the tool schema: the model cannot see the browser build or host OS, so asking would buy a plausible guess in place of a fact. The browser label is read once in `__enter__` (a version can't change mid-session, and the alternative does work on the failure path at the worst moment) and every read is defensive — a crashed page answers for neither URL nor viewport, which must cost the detail, never the finding. After every charter, one best-effort LLM call writes the per-requirement `summary` (an `LLMError` logs and leaves it null rather than failing the run; recoverable via `POST /exploratory-runs/{id}/summarize`, which 422s unless the run is `completed`). The two **summary** calls — `summarize_exploration` and the forced session wrap-up — are the only retried LLM calls in the codebase (`_SUMMARY_ATTEMPTS`, 2), and they earn it by being the only ones whose input can't be cheaply reproduced: a charter or plan regenerates from rows still in the database, but a summary reads session sheets from a browser run that cost the sum of its charters. Both **heartbeat per attempt** (the run summary via a new `on_attempt` callback wired in `_write_summary`, the wrap-up via the `on_round` it already had), which is load-bearing: the worker calls them while the run is still `running`, so without it a retry could out-wait `HEARTBEAT_STALE_SECONDS` and have the reconciler re-enqueue a nearly-finished run. That heartbeat is also what keeps the attempt count a pure cost decision instead of arithmetic against `OPENAI_TIMEOUT`. The wrap-up additionally **never raises**, in three degrees: retry, then fall back to the raw message text when the JSON won't parse (the same salvage the idle-rounds exit does), then — if the request itself never succeeds — report that failure _as_ the notes. The reason is that `action_log` exists only inside `run_exploration_loop`'s frame, so any exception has `_run_one_session` mark the session `error` and discard the whole record of a charter that already spent its action budget driving a browser; exploration is over by the time the wrap-up is asked for, so a failure there should cost the notes, never the session. A transport failure during an **acting** round still raises, and should: there the session was genuinely cut short, so `error` is the honest status. A failed run can be restarted (uncapped) — completed sessions are skipped, the in-flight charter restarts from scratch since a half-explored browser died with the worker, and findings already persisted are kept (its `actions_used` is reset to 0 when the charter is re-entered, since the count describes an attempt that no longer exists). Both the run detail page and the session sheet poll every 2.5 s while their row is `pending`/`running`; the live progress they show comes from `run_exploration_loop`'s `on_round` callback, which — unlike `_complete_with_tools`'s bare heartbeat — carries the running action count, so `ExploratorySession.actions_used` climbs during the session (and survives a session that dies mid-charter) instead of being written once at the end. Finish-sprint sweeps `pending`/`running` runs to `failed` (fourth `_SWEEP_SPECS` entry, joining straight to `Sprint` since a run carries its own `sprint_id`). Sprint-list cards deep-link to the test-runs page when either run type exists.

**Issue-tracker integration** (`routes/issue_tracker.py` + `services/issue_tracker.py` + `services/finding_dedup.py` + `services/finding_export.py`): a sprint can be connected to a **Jira project** or a **GitHub Issues repo** (`IssueTrackerConfig`, one row per sprint, never both providers) from the test-runs page, after which a run can file its **bug** findings there. `issue` findings never file — they say the testing was obstructed, not that the product is wrong, so there is no verdict about the product to relay. Credentials are Fernet-encrypted at rest exactly like `Repo.github_token`, never serialized, never logged, and **verified against the live tracker inside the request on every save** — first connect and every edit alike, since the only moment a credential problem is cheap to fix is while the user is looking at the form. `TrackerError` → 422 (reachable, and it said no), `TrackerUnavailableError` → 502 (no answer at all); nothing persists unless verification succeeds. There is deliberately no background re-verification: it would need somewhere to put a result nobody is waiting for, and would put outbound tracker calls on a web-process sweep. A token revoked between edits surfaces where it is actionable — as `tracker_error` on the findings, next to the button that retries them.

Connecting **GitHub Issues** offers the sprint's own repository (`use_sprint_repo`, GitHub-only — 422 with any other provider): the sprint is already bound to a `Repo`, so `owner/repo` is derived server-side from `Repo.github_link` via `parse_github_url` (the payload's `target` may be blank, and a repo link that is not a GitHub URL 422s) and a blank `api_token` falls back to `Repo.github_token`. The whole option resolves into an ordinary config before verification — the token is decrypted, verified, and re-encrypted exactly like a typed one, so it is a **copy taken at save time**. Rotating the repo's token later does not follow through (the user re-saves), which is the price of `IssueTrackerConfig` gaining no column and `finding_export`, both retry routes, and every `TrackerConfig` construction being untouched. `_resolve_token`'s order is: typed → repo's (when the flag is set) → the stored same-provider one → 422. The repo's sits **above** the stored one on purpose: it is what lets a user move an existing connection onto the repo's token by ticking the box and clearing the field, and it is the one legitimate exception to "a token is required when the provider changes", since this token is GitHub's by construction rather than the previous tracker's. A repo registered without a token is ordinary — public ones need none to read — so its absence falls through rather than failing the save, and `Repo.has_access_token` (a serialized property, never the token — Convention #10) is what lets the modal say so before Save rather than after. Note that `verify` only reads, so a read-scoped repo token connects fine and fails at the first ticket as `tracker_error`; the modal's hint says so, and this is the same reason `_verify_github` deliberately does not check `permissions.push`.

The config is **editable**, provider switch included. Three rules: a blank token means "keep the stored one" on a same-provider edit (re-entering a secret to change a project key is the friction that gets tokens pasted into chat windows); a token is **required** when the provider changes, since a Jira API token is meaningless to GitHub and reusing it would verify nothing; and provider-irrelevant fields are cleared on a switch, so a stale Jira site can never linger on a GitHub config. Already-filed findings are untouched by an edit — their `tracker_issue_url` still points where they were actually filed, and `tracker_target` (`"{provider}:{target}"`, stamped at file time) keeps them out of the new tracker's de-duplication window. That column exists for one specific failure: **GitHub issue numbers are per-repo integers**, so without it repo B's `#7` answers `issue_is_open` for repo A's `#7` and a finding gets attached to an unrelated ticket. On Jira the same mistake merely 404s and files fresh. Disconnecting is never blocked by a run in flight — that run's export fails into `tracker_error`, which is already handled.

**Export runs at exactly two automatic call sites** — immediately after the `COMPLETED` commit in each task, placed **after** that commit and **outside** the `try` that feeds `_record_failure`, so a slow or failing tracker can never turn a finished run into a retry that re-executes every case or re-drives a browser through every charter. One rule, no special cases: **a run that finished reports its bugs automatically; anything else waits for a human.** Every abnormal ending — superseded by an upstream edit, retries exhausted, sprint finished underneath it, worker crash — leaves a finding set that is incomplete _and known to be incomplete_, and that is not written unasked into a tracker other people read. Deliberately **not** called from `_fail_execution`, `_fail_run`, `_record_failure`'s terminal branch, `finish_sprint`, or the reconciler sweeps — unlike `abandon_unreached_children`, which those paths do call. The distinction: that helper settles rows the run already owns, this one writes to a third party. Those findings are not stranded — they stay on the run page and `POST /test-runs/{id}/export-findings` / `POST /exploratory-runs/{id}/export-findings` (synchronous, uncapped, modelled on `summarize`) file them on request, which is also the retry path for a filing that failed.

That placement has one consequence on the frontend, and it shipped as a bug: a run's status reads terminal **before** its findings are filed, so a page that polls only while the run is in progress tears its own interval down inside the export window and then shows "N bugs not yet filed" until someone reloads. Both run detail pages therefore keep polling — bounded to `EXPORT_GRACE_TICKS` (48 ≈ 2 min) — while a **completed** run has the toggle on, unfiled bugs, and no `export_error_count`, which is exactly "the automatic export is probably still running". Bounded rather than open-ended, and keyed on `completed` rather than any terminal status, because every other way to reach that combination is a standing state, not a pending one: a failed run never calls export at all, and every known bad ending inside `_export` — a tracker disconnected mid-run included — writes `tracker_error` and so fails the `export_error_count === 0` half.

The run's toggle governs only the **automatic** half, and `export_findings(session, parent, *, requested=False)` is where the two halves part. The tasks call it with the default and a toggle-off run files nothing; the retry routes pass `requested=True`, because a user pressing "File 6 bugs" _is_ the consent the toggle stands in for. Reading the toggle there instead was a shipped bug worth naming: the roll-up counts every unfiled bug regardless of the toggle, so the button rendered and did nothing — 200, no ticket, no error — which took away the only recovery for a run started before a tracker was connected. The `not rows` half of the fast exit stays unconditional, so a run with no bugs is still a no-op rather than a trap. `ExportRollup` carries `export_findings` itself so the page can word the difference ("This run was not set to file findings automatically") without changing what the button does.

**Grouping precedes filing**, and the grouping is the shared one described under [Defect grouping](#key-flows) below rather than a second opinion computed here — `_export` calls `assign_defect_groups` itself, immediately after its fast exit, so a run filed by hand after never completing is grouped before anything irreversible is written. This is not a new responsibility: filing has always grouped first, and what changed is that the answer is now persisted and shared instead of private. The common retry costs nothing, because a completed run's rows are already grouped and the pass fast-exits. Inside that shared pass the two stages are: a deterministic prefilter that normalizes `title + expected + actual` (casefold, strip accents, drop punctuation **and digits** — a generated order id differs per run while the defect does not) and collapses exact matches; this is the common case, since one broken dependency fails every case in a plan with the same words, and it costs no LLM call at all. What survives goes to one `llm.group_findings` call, which catches paraphrases sharing no tokens ("checkout returns 500" / "the order endpoint errors on submit"). The prompt is deliberately conservative — a defect wrongly split costs a few minutes of triage, one wrongly merged disappears — and grouping judges **sameness only**: whether a finding is real was settled by the run that recorded it, and re-opening that question is how a genuine bug gets talked out of existence on the way to the tracker (which is also why the call has no tools and no repo access). The module **never raises**: an `LLMError` degrades to the prefilter's answer, which is a worse grouping rather than no grouping. The representative whose report becomes the ticket is elected **in code** (highest severity, then lowest position), never by the model, since the ticket's title and body come from that row — and it is elected from a **live row** rather than taken from the `DefectGroup`'s frozen text, because a ticket body needs steps, severity, environment, and a screenshot path that only the row carries. A key the model invented is ignored — adopting one that names no group would attach a finding to nothing.

De-duplication is now **one indexed lookup, no fork**: the defect's `DefectGroupTicket` row for the current `tracker_target`. No row for this target means this defect has never been filed _here_, so it files fresh — the defect is the same, the tracker is not, and the team is looking at the new one. That replaced a sprint-wide scan of findings already carrying a key (`_already_filed`, `_filed_rows_with_key`, `_existing_url`, all deleted): the adopted URL now comes off the column the filing itself wrote instead of being reconstructed from whichever finding happened to record it. The target scoping is not optional in the other direction either — GitHub issue numbers are per-repo integers, so an unscoped lookup would adopt repo B's `#7` for repo A's, the exact failure `tracker_target` exists for. A `("text", …)` bucket has no group and therefore no ticket to adopt, so it files fresh; that is the whole of the ungrouped handling, reachable only if the pass above hit an unexpected exception. Filing still goes ahead there — a grouping problem must cost a duplicate, never an unfiled bug, the same asymmetry `issue_is_open` rests on — but note the consequence **outlives the run that caused it**: an ungrouped bucket records no `DefectGroupTicket`, so once a later pass groups those rows, the next run joining that group finds nothing to adopt and files a second ticket. Exactly one, since that filing writes the row and every run after it adopts — so the state repairs itself rather than leaking per run. `_export` logs a warning naming the run when it files an ungrouped bucket, because that duplicate surfaces a run or two later and is otherwise untraceable to the failure behind it. After a successful create the row is **upserted** — the unique constraint makes that the only legal move rather than a preference — with `filed_at` advanced explicitly, since a `default_factory` fires on insert only. The insert sits inside a `session.begin_nested()` savepoint and an `IntegrityError` re-reads instead of propagating: it shares the per-group commit with the receipts, which runs _after_ `create_issue` already succeeded, so an escaping error would leave a ticket in the tracker that no finding carries the key of. Before adopting a match, `issue_is_open` checks it; a closed ticket is a decision somebody made, so a new one is filed carrying a `Previously filed as …` back-reference rather than the old one being silently reopened. `issue_is_open` never raises and answers `False` on any doubt (404, revoked token, tracker down) — the failure directions are not symmetric: a wrong "closed" costs a duplicate, a wrong "open" attaches a finding to nothing and loses it. Adopting is deliberately silent (no comment on the ticket): the findings are all readable in-app, and appending on every re-run is noise. Per group the representative and its duplicates get the same key/url, duplicates additionally `tracker_is_duplicate = True`, committed per group so a mid-way failure keeps what already landed. On a `TrackerError` **every member** gets `tracker_error` and no key, so a retry re-elects and re-files the whole group. Exploratory screenshots are attached (Jira only — GitHub has no issue attachment API) for the representative alone; `None` path, missing file, or a failed upload all skip silently, since `STORE_OFFLINE=false` makes the absence normal.

Everything outbound is **redacted inside `create_issue`**, not at the call sites — a ticket is the one artifact that leaves this application, so the guard belongs at the exit. The rule is the exploratory one applied to prose: exact values from `TestEnvironmentAccess.env_vars` minus the base URLs (a bug report has to be allowed to name the page it is about), matched as **substrings** rather than whole values, since a credential leaks into `actual` mid-sentence. Substring matching is bounded by `_MIN_REDACTABLE_LENGTH` (6) — blanking a two-character value would gut the report while protecting nothing. The Jira body is **ADF** (`{"type": "doc", "version": 1, …}`, paragraph/heading/bulletList only): v3 rejects a plain-string `description` with a 400, so this is the contract rather than a formatting preference. The payload is held to `project`/`summary`/`description`/`issuetype`/`labels` — instance-specific required fields are the commonest cause of a 400 — and severity rides as a label (`severity-high`) rather than as `priority`, which is instance-configured. GitHub `verify` requires `has_issues` but deliberately **not** `permissions.push`: a fine-grained token can hold Issues:write without push, and requiring it would reject exactly the narrowly-scoped tokens worth creating.

The run-start toggle (`export_findings` on both `TestRun` and `ExploratoryRun`) is decided once, at creation, and 422s when set with no tracker connected; both modals check it by default when a tracker is present, since connecting one is itself the statement that findings should go there. Both run shapes carry an export roll-up computed at response time (Convention #10): `exported_finding_count`, `exported_issue_count`, `export_error_count`, `unexported_finding_count`, and `export_groups` — the groups themselves, not just counts, so the page can answer "which four findings became QA-142?" without the reader inferring it from the cards. `export_error_count` is a **subset** of `unexported_finding_count` rather than disjoint from it: one condition decides whether the page offers the button, the other words it ("File 6 bugs" for a run that never filed, "Retry" for one that tried and failed). A ticket's provenance trailer names the run that produced it (`Scripted run 14` / `Exploratory run 10`, built in `finding_export._spec_for`), so both run detail headers and both test-runs list rows display that id — it is a global surrogate key that otherwise appears only in the URL, leaving a ticket reader nothing to match against. Shown as `#14` deliberately: it is an identifier, not this sprint's fourteenth run. `FindingCard` links the ticket, marks a grouped finding `(grouped)`, and shows the filing error inline — source-agnostic, so both modes inherit it from `FindingBase`.

**Defect grouping** (`services/finding_grouping.py` + `DefectGroup` + `DefectGroupTicket`): a sprint remembers its **distinct defects**, so "how many bugs did this sprint find" is answered by counting defects rather than finding texts — paraphrase-aware, and **with no issue tracker connected**, which is what the old text-only fallback could not do. `assign_defect_groups(session, parent)` runs at exactly the same two automatic call sites as `export_findings`, immediately **before** it (the ordering is load-bearing and commented at both: export files one ticket per group, so the grouping must be committed first), plus once inside `_export` itself — three call sites in total, and the task-level pair cannot be dropped in favour of the export one, because `_export` fast-exits when no tracker is connected and grouping without a tracker is the whole point. One rule, no special cases: **grouping happens when a run completes, and again before anything is filed.**

The pass is **append-only**: a finding joins an existing group or opens a new one, and no group and no existing membership is ever rewritten. That is what makes the panel's numbers stable between polls — the non-deterministic judgement is resolved once, at completion, and frozen in a row, rather than recomputed by an endpoint polled every 2.5 s (the rejected Approach 4, which also raced with itself). A group's three text fields are **frozen at creation**, because they are what the model is shown as the sprint's known defects on every later run; a representative re-elected per run would describe the same defect differently each week and make matching progressively harder. There is deliberately **no `severity` column** — severity is the max over the members, derived where it is already derived, the same argument `TestCaseExecution.finding_type` rests on — and no stored `dedup_key` with a unique constraint, which was tried and cannot work: the colliding findings are paraphrases from separate per-case `diagnose_and_fix_script` calls, so they never share text and the constraint would never fire across executions.

Mechanically it reuses `finding_dedup` unchanged, with the match targets being stored `DefectGroup` rows rather than filed tickets — the existing `{"groups": [{"indices": [...], "existing_key": …}]}` shape already means "these join that / these open a new one", so only a rename (`FiledFinding` → `KnownDefect`, `issue_key` → `key`, an opaque identity the module never inspects) and a prompt re-wording were needed. Four properties are deliberate. **A clean run pays nothing**: the fast exit sits before the sprint-wide `DefectGroup` read, not merely inside `group_findings`' own empty-input guard, because by the time that fired the query building its argument would already have run. It **filters to `BUG` itself** rather than trusting the caller, since the grouping machinery is type-blind by design and a merged bug-and-issue would surface only as a bug count one too low. It **skips rows that already carry a group**, which is what makes it idempotent across a restart. And it takes a **`SELECT … FOR UPDATE` on the sprint row before the known-defect read** — the deployment runs several workers and a `TestRun` fans out into a job per `TestExecution`, so siblings routinely finish together and would each be shown a list missing the other's groups; reading a stale list is the bug, so the lock goes before the read, and `with_for_update()` renders on PostgreSQL and is silently omitted on SQLite so the test engine needs no branch. Like `finding_dedup` and `finding_export` it **never raises**, and it additionally **rolls back** on failure, because the caller runs `export_findings` on the same session immediately afterwards.

`DefectGroupTicket` is a child table rather than three columns on the group, because a defect can outlive the tracker it was first filed to: one triple would be overwritten on a switch, and switching **back** would then file a duplicate of a ticket that already exists and is probably still open. `UNIQUE (defect_group_id, tracker_target)` states the invariant in the schema — one defect gets at most one ticket in any given tracker. Note the claim is about the **row**, not the tracker: nothing serializes `_export` itself, so two sibling jobs can still both create an issue for one defect. That is pre-existing (the old `_already_filed` had the identical stale-read problem), visible (a duplicate a human closes, not a lost defect), and deliberately not fixed here — holding the sprint lock across `_export` collides with its per-group commits, which exist so a mid-way tracker failure keeps the tickets that already landed, and would hold a lock across outbound calls to a third party.

One consequence to expect rather than debug: **`bug_count` is monotonic within a sprint.** Fixing a bug does not lower it. Run 1's failed row keeps its finding and its group forever, and run 1 is still `completed`, so the sprint still found that defect; a regression later rejoins the original group rather than opening a second one. The panel reports what the sprint's testing _found_, not what is currently open.

**QA metrics** (`services/qa_metrics.py` + `GET /api/sprints/{id}/qa-metrics` + `SprintMetricsPanel`): a per-sprint panel above both run lists on the test-runs page — how much was tested, how many distinct defects came out of it, two defect densities, and a per-requirement breakdown. One pure function over eager-loaded rows, computed at response time and **never stored**, which is the shape `export_rollup` already established for exactly this problem one level down; there is therefore no schema change and no migration (Convention #11 vacuous). It **never raises**, following the `finding_dedup` / `finding_export` contract for a reason of its own: the page polls this endpoint every 2.5 s, and a metrics panel must not be able to 500 the page it decorates. The endpoint is a pure read — no LLM call, no write — and both relationship chains (`test_runs → executions → cases`, `exploratory_runs → sessions → findings`) are `selectinload`ed, guarded by a test asserting the query count stays flat as runs are added rather than pinning a literal.

Three counting rules carry it, and each exists to stop a number moving for a reason that has nothing to do with testing. **Only `completed` runs count**, mirroring the export rule exactly (_a run that finished reports; anything else waits for a human_): an aborted or in-flight run's finding set is incomplete _and known to be incomplete_, and its case denominator under-counts because the cases it never reached never ran — excluded runs are counted and named (`excluded_runs_running` / `excluded_runs_failed`) rather than silently dropped. **Scripted cases are counted at two levels that never mix**: `distinct_test_cases_run` is the density denominator, `case_executions` plus its passed/failed/errored split describes how much testing was done, and a case run three times adds 1 to the first and 3 across the second. Dividing by executions would make a sprint read three times healthier for re-running an unfixed plan — a metric that rewards noise — and keeping the levels apart is also what removes any need for a "what status does that case _have_?" tiebreak. Exploratory sessions stay cumulative and are **never summed with** the scripted counts (a 25-action browser session and a 3-step script are not the same unit); charters are generated fresh per run, so every session is already distinct. **One bug is one defect**, keyed three ways in order: the `DefectGroup` the assignment pass assigned at run completion, then `(tracker_target, tracker_issue_key)` where a ticket exists — the pair, never the bare key, since GitHub issue numbers are per-repo integers — then `finding_dedup.dedup_key`, shared rather than reimplemented so the panel and the tracker cannot report different groupings of the same findings. Uniformly tagged tuples (`("group", …)` / `("ticket", …)` / `("text", …)`), so three kinds of identity cannot collide in one dict. **The stored group outranks ticket identity**, which reverses the precedence this paragraph used to argue for: a `DefectGroup` is not text similarity but the same judgement, made once and remembered, and the tracker-switch case settles it — ticket identity keys on the _pair_, so one defect found either side of a switch would count as two bugs. `tracker_target` guards a _filing_ hazard and must not reach the headline. The ticket branch survives beneath it for rows the pass never grouped. Paraphrase grouping is therefore now available with no tracker connected, and still costs this endpoint nothing: it happened at run completion (see [Defect grouping](#key-flows) above), and `defect_group_id` is a raw column on rows already eager-loaded — no new `selectinload`, no new query, nothing dereferenced into a `DefectGroup`. A group's severity is the **highest** among its members, mirroring `finding_dedup.elect_representative`, so a high-severity defect cannot hide behind a medium duplicate; **issue findings are never collapsed at all** — an issue records that testing was obstructed, not that the product is wrong, so "how many distinct defects" is not a question it answers, and collapsing three cases blocked by one unreachable environment would understate how much of the run was lost; counting them raw also keeps `issue_count` in the same units as `executions_errored` beside it. A consequence worth knowing: per-requirement issue rows sum to the issue headline _exactly_, while bug rows may sum above it.

Two denominator decisions are the non-obvious ones. `bugs_per_requirement` divides by **`requirements_covered`**, not `requirements_total`: a sprint that tested 1 of 5 features must not spread its real bugs across 4 nobody touched, which would report a fifth of the true density and improve every time an untested requirement is added. `requirements_total` (confirmed live requirements) is surfaced beside it so coverage stays legible rather than being baked invisibly into the ratio — it is display-only, and nothing divides by it. It can legitimately read **below** `requirements_covered`: coverage is what runs already did, while the total is a live snapshot, so a covered requirement later edited (back to `analyzing`) or archived leaves the two crossed. That is why the tile states them as two facts rather than as a fraction — `1 of 0 requirements covered` reads as a broken panel and costs the reader's trust in the tiles beside it, and "currently" is the word that makes the crossed case self-explaining. Both densities are `float | None`, null when their denominator is zero, so the panel renders `—` and no TSX needs a divide guard. Scripted findings are gated on `finding_title` exactly as `TestRun.bug_findings` is — the fourth consumer of that predicate — not for legacy rows (live code writes the finding fields as a group, so a titleless verdict is unreachable) but because `bug_findings` is what `export_rollup` counts and what the run pages display: counting by `finding_type` alone here would let the run page report three bugs beside a panel reporting four, with nothing to say which is right. `per_requirement` includes **every** covered requirement, findings or not — a tested-and-clean requirement is a result worth showing — ordered by bug count descending then by name, with archived requirements present and flagged (their bugs are in the headline, so hiding the row would make the numbers not add up). Rows may legitimately **sum above the headline**, since grouping is sprint-scoped and one broken dependency breaks login _and_ checkout; the panel footnotes that only when the two actually differ. The alternative — electing an owner requirement per group — would make a requirement with real failures read as zero, a worse lie than a number needing one sentence. On the display side, density renders in the unit it is computed in (bugs per case, 2 dp) with `< 0.01` whenever the value is above zero but rounds to zero: `—`, `0.00`, and `< 0.01` are three distinct readings — nothing tested, tested and clean, tested and barely-dense — and "0.00 bugs / case" on a sprint that found bugs is the one output that tile must never produce. Wiring the panel into `TestRunsPage` also required giving its `shouldPoll` the `exportPending` clause the two run detail pages already carried (same `EXPORT_GRACE_TICKS` budget): the panel's bug count depends on tracker keys, which arrive _after_ the run reads terminal, so a purely `running`-based condition tore itself down inside the export window and froze the panel until a reload.

**Post-confirmation editing** (`services/invalidation.py`): the pipeline used to be a one-way ratchet — a `confirmed` requirement, a `confirmed` environment, and an `approved` plan were all frozen, which is what kept everything downstream consistent for free. All three are now editable, and one module owns what an edit invalidates because four callers need the identical answer (requirement edit, add, delete, and the PRD bulk replace, which is a delete _and_ an add at once). Nothing in it commits: it stages on the caller's session so an edit and its cascade land in one transaction. The rules are deliberately asymmetric — **editing** a requirement removes its plan (written against text that no longer exists) and un-confirms the environment; **adding** un-confirms the environment but removes no plan (existing ones describe their own unchanged requirements); **deleting** removes only its own plan and leaves the environment `confirmed`, because `TestEnvironmentAccess.requirements_stale` already argued that removal can only shrink the environments needed. An **environment** change (content _or_ extracted variables) removes every plan in the sprint; a **plan** edit returns it to `draft`, so approval keeps gating whether it can run. Re-checking unchanged text is not a change, and the Re-check button — which the UI itself points the user at after a requirement edit — must not be able to destroy the sprint's plans. Comparing before cascading is not enough to guarantee that: the re-check re-ran `generate_env_vars`, and any drift in that non-deterministic call read as a variables change and cascaded. The comparison stays, but the guarantee comes from `_resolve_env_vars_json` not re-extracting identical text at all (see Test environment access above). **Edits are never blocked on work in flight.** A route-level guard was tried and removed: it could not be made airtight against a concurrent request, so it bought no safety — only a blocked edit for the length of a run. Nothing faults without it, which was verified rather than assumed: `generate_test_plan` discards its result through the status re-check it already had, and `execute_test` keeps resolving its cases because they are _archived_, not deleted. Instead the workers stop themselves — `execute_test` between cases and `explore_requirement` between charters check `outdated` and bail with `SUPERSEDED_ERROR`, which saves the remaining LLM calls without refusing the user's edit. The exploratory check deliberately ignores the `test_plan` reason: a charter's cases were consumed once at generation time, so a plan edit does not invalidate a session already under way. Removing a plan archives and **detaches** its cases (`test_plan_id = None`) and deletes the plan row — archiving the row in place would collide with `TestPlan.requirement_id`'s unique constraint and leave no slot for the regenerated plan. **Nothing regenerates it automatically**, and the removal is invisible in the plan list, because a requirement with no plan contributes no row: the test-plans page therefore showed every surviving plan approved, announced "All test plans approved", offered Continue to Test Runs, and hid the Generate button (it rendered only when there were _no_ plans at all), leaving the edited requirement silently untestable. `Sprint.test_plans_missing` closes that — a computed flag (Convention #10) mirroring exactly what `generate_test_plans` would create, so the page can offer regeneration precisely when pressing it would do something. It stays false while the edited requirement is back in analysis and goes true when it is confirmed again, at which point the page offers "Generate missing test plans" — or, if that same edit also re-opened the environment, a link to re-check it first, since generation 422s until then. Completion is now read from `test_plans_complete` rather than re-derived in the frontend, for the same reason: a missing plan is not a plan that falls short. Requirements are archived only when a run references them; one with no history is deleted outright, which keeps the PRD re-upload path from accumulating invisible rows.

**Run staleness** (`models/database.py::outdated_reasons`): a run records the three `content_revision` values it executed against (`requirement_revision` / `plan_revision` / `env_revision` on both `TestExecution` and `ExploratoryRun`), and an inequality later means it no longer describes the current sprint. Revisions rather than timestamps because `updated_at` is stamped by confirm, approve, restart, and confirm-all — none of which change what a run was testing, so a plan approved after a run started would have marked that run outdated. Deletion is folded in as the limit case of change rather than a parallel flag: an archived requirement yields the `requirement` reason, so `outdated == bool(outdated_reasons)` holds everywhere and the restart guard is one condition. `requirement_deleted` survives only to pick the badge wording. `outdated` itself is **not serialized** — the frontend derives it in `src/outdated.ts::isOutdated`, rather than carrying two fields that must agree. A missing plan counts as outdated; a missing environment row does not, and the asymmetry is deliberate: plans are removed by the cascade precisely when content changed, so absence is evidence, while an environment row cannot be deleted through any flow. Every column defaults to `0` on both sides, so pre-existing runs read as current with no backfill. Restart is refused on any outdated run (both run types) — the remedy is a new run.

**Terminal parents leave no non-terminal children** (`services/finalization.py`): `TestCaseExecution` and `ExploratorySession` rows have exactly one writer each — the loop in `tasks/execute_test.py` and the one in `tasks/explore_requirement.py`. That is fine while a job runs to the end and wrong every other way it can stop. A superseded run, a finished sprint, a plan un-approved under the job, an exhausted retry counter, a worker killed mid-case: each finalized the parent and returned, leaving children `pending` forever — or `running` forever, spinning, when the worker died after the row was stamped. The user saw a run reading `failed` above a list of cases still labelled "Queued", and there was no self-healing path, because the commonest cause (an upstream edit) also makes the run outdated, which `restart_test_execution` refuses. So one module owns the invariant, in the shape `invalidation.py` established: `abandon_unreached_children` marks every non-terminal child `skipped`, stages without committing so the parent's failure and its children's disposition are one transaction, and is called from the two tasks' single failure chokepoints (`_fail_execution` / `_fail_run`, which between them cover all seven job-start guards and both mid-run supersede exits), from `finish_sprint`, and from the reconciler's three failing branches via `_SweepSpec.child_spec`. Three things are deliberate. It is **not** called on the branches that send a parent back to `pending`: a `running` child there is exactly what the next attempt resumes from, so settling it would be the same bug in reverse. `skipped` is **not** in either task's finalized set, so a restart re-runs those children and the row never carries a stale verdict forward — which is also why no route needed a matching reset. And the pending-vs-running distinction lives in the row's `error` rather than in a second status, because it changes what the reader should do: a `pending` child provably never touched the test environment, a `running` one may have executed a script or driven a browser against it before the worker died. One data-only startup migration (`_settle_orphaned_children`) repairs rows stranded before all this existed.

## Authentication

Shared-secret password gate backed by an HttpOnly session cookie. Optional — when `APP_PASSWORD` is unset the app is fully open.

- `backend/utils/auth.py` — `verify_auth(request)` dependency: reads `qa_auth` cookie, compares via `secrets.compare_digest()`, raises 401 on mismatch, passes everything when `APP_PASSWORD` unset.
- `backend/routes/auth.py` — unauthenticated: `POST /api/auth/verify` (sets cookie on match), `GET /api/auth/check` (reports state, never 401s).
- Protected: the `/api/repos*`, `/api/sprints*`, `/api/requirements*`, test-environment (`/api/sprints/{id}/test-environment`, `/api/test-environment/*`), `/api/test-plans*`, test-execution (`/api/sprints/{id}/test-runs`, `/api/test-runs/*`, `/api/test-executions/*`, `/api/test-case-executions/*`), exploratory (`/api/sprints/{id}/exploratory-charters/*`, `/api/sprints/{id}/exploratory-runs`, `/api/exploratory-runs/*`, `/api/exploratory-sessions/*`, `/api/exploratory-findings/*`), and issue-tracker (`/api/sprints/{id}/issue-tracker`) routers use `dependencies=[Depends(verify_auth)]`. `/api/health` and `/api/auth/*` are open.
- Cookie: `qa_auth=<password>; Path=/; SameSite=Strict; HttpOnly` (session-scoped).

## Testing

### Backend (`backend/tests/`, pytest)

- `conftest.py` has an **autouse fixture that replaces the PostgreSQL engine with in-memory SQLite** (`sqlite:///file:test_db?mode=memory&cache=shared&uri=true`) and no-ops `init_db` — no test ever touches a real database. It also sets a fresh `ENCRYPTION_KEY`, disables dotenv, and deletes `SSL_CERT_FILE` (a Windows footgun that breaks httpx client creation).
- `async_client` fixture: httpx `AsyncClient` over `ASGITransport`, auth disabled (`APP_PASSWORD` deleted), Redis health check mocked, `get_session` overridden to the SQLite session.
- A second **autouse fixture (`_isolate_redis`) no-ops `QueueService._connect`** — no test can enqueue to live Redis; the degraded service returns `None` from `enqueue_analysis`. Tests that assert enqueue behaviour monkeypatch `get_queue_service` with a recording stub.
- GitHub API calls are mocked with **pytest-httpx** (`httpx_mock` fixture); `conftest.pytest_collection_modifyitems` relaxes its assert-all-consumed defaults. Use the shared `_create_repo(client, url, httpx_mock)` helper to seed repos through the API.
- LLM calls never hit the network: `test_llm.py` stubs `_get_client`; task/route tests monkeypatch `services.llm` functions. The task and reconciler are tested as plain functions against the SQLite fixture (`new_session` picks up the patched engine); intermediate statuses are seeded directly via `db_session` (see `_seed_sprint`/`_seed_requirement` in `test_requirement_routes.py`).
- Exploratory testing never launches a real browser: task tests monkeypatch `services.browser_session.BrowserSession` and both `services.llm` exploratory functions; `test_browser_session.py` mocks Playwright itself (a `_FakePage`/`_FakeLocator` pair) so the executor logic — origin lock, secret handling, the never-raise contract — is covered without a browser binary in CI. As with script execution, **the browser layer's real correctness can only be established by manual e2e.**
- Issue-tracker calls never reach the network: `test_issue_tracker.py` drives the transport against **pytest-httpx** (which intercepts the new _synchronous_ client too, so no tracker call can escape from any test), and everything above it monkeypatches `services.issue_tracker` / `services.finding_export` — the same treatment `services.script_runner.run_script` gets. No test holds a real credential; tracker configs are built with dummy tokens and `conftest.py` already provides a fresh `ENCRYPTION_KEY`. Existing run tests are unaffected because `export_findings` fast-exits on the column default (`False`).
- Test execution never runs a real subprocess/browser in task or route tests: `services.script_runner.run_script` is monkeypatched (`test_execute_test.py`) exactly like `services.llm` functions elsewhere. `test_script_runner.py` is the one place real subprocesses run — plain Python scripts only, no Playwright/browser dependency, so it stays fast and CI-safe.
- The reconciler loop starts via FastAPI lifespan, which httpx `ASGITransport` never runs — it is inert in API tests; `reconcile_once` is unit-tested directly.
- Auth-specific tests (`test_auth_routes.py`) build their own client with `APP_PASSWORD=secret123`.

### Frontend (Vitest + Testing Library)

- Config lives in `vite.config.ts` under the `test` key (jsdom, `globals: true`, setup file imports `@testing-library/jest-dom/vitest`).
- Tests are colocated with source (`*.test.tsx` next to the component).
- `src/test/test-utils.tsx` exports `renderWithRouter(ui, { initialEntries? })` — wraps the component in `createMemoryRouter` + `RouterProvider` with a catch-all route.

Pinned by `test_finding_carries_its_issue_tracker_receipt`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **`issue_is_open` resolves every doubt to `False`**                                              | Its failure directions are not symmetric: reporting a live ticket as closed costs a duplicate, while reporting a missing one as open attaches a finding to nothing and **loses** it. So a 404, a revoked token, and an unreachable tracker all read as closed, and the function never raises. Keep it that way if you extend it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **A run reaches a terminal status before its findings are filed**                                | Export runs _after_ the `COMPLETED` commit and outside the task's `try` (deliberately — see the flow above), so between the two the run reads `completed` with every bug still unfiled. A run page that polls only on `pending`/`running` therefore stops polling inside that window and shows "not yet filed" until a manual refresh; that shipped on both detail pages. Any future UI that reacts to a run finishing must treat the tracker receipt as arriving **later** than the status, not with it — `EXPORT_GRACE_TICKS` on `TestRunDetailPage`/`ExploratoryRunDetailPage` is the bounded extra polling that closes it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **`STORE_OFFLINE=false` means exploratory findings have no screenshots**                         | `StorageService.store_screenshot` no-ops when offline mode is disabled, exactly like `store_readme`/`store_prd`. That is the documented outcome of the setting, **not a failure**: `record_finding` must persist the finding regardless, `ExploratoryFinding.screenshot_path` stays `None`, `GET /exploratory-findings/{id}/screenshot` 404s, and `FindingCard` renders without an image rather than a broken one. Don't "fix" a missing screenshot by failing the finding.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

### Redis / RQ (active — requirement analysis)

RQ workers process requirement-analysis jobs (revived from the removed word-count pipeline around commit `ab337c1`). Hard-won lessons, now applied in code:

- **Windows has no `os.fork()`**: `worker.py` uses `SimpleWorker` when `sys.platform == "win32"`. `QueueService._connect` sets a 5 s socket timeout for enqueue-side Redis calls (enqueue, ping, job lookups); RQ itself bumps the worker connection's timeout above its blocking-dequeue window on startup, so dead-connection hangs are bounded on both sides.
- **RQ's `job_timeout` hard-kill also needs fork**: it stays as a Linux-side backstop; on Windows the analysis task's only long wait is the LLM call, which `OPENAI_TIMEOUT` bounds. Crashed/hung workers are caught by the DB heartbeat + reconciler instead.
- **One `QueueService` per process**: lazy module-level singleton (`get_queue_service()` / `reset_queue_service()`), never constructed per-request. Degrades gracefully (`enqueue_analysis` returns `None`) when Redis is down — rows stay `pending` and the reconciler enqueues them on recovery.
- **Tasks are enqueued by dotted string path** (`backend.tasks.analyze_requirement.analyze_requirement_task`), so the web process never imports task modules. Task modules must not import from `backend.services.queue` or `backend.worker` (circular-import rule).
- **Redis is transport only**: no `job.meta` status; PostgreSQL rows carry the whole lifecycle, making every enqueue idempotent (the task no-ops on rows that aren't `pending`/`analyzing`).

## Conventions and Notes

1. **Working directory**: repo root for backend commands; `cd frontend` for frontend commands.
2. **Python imports**: `backend.`-prefixed (`from backend.config import ...`). Always run modules as `python -m backend.main` from the repo root, never `python backend/main.py`.
3. **Planning docs**: feature plans live in `thoughts/plans/`, implementation tracking in `thoughts/implementations/` (git-ignored).
4. **Response types**: every endpoint declares a `response_model` from `models/types.py`; table models stay in `models/database.py`.
5. **Error handling**: raise `HTTPException` with a helpful `detail`; the global handler catches everything else as a 500. GitHub failures map to 422 (validation-time) or 502 (fetch-time).
6. **Frontend error parsing**: FastAPI `detail` can be a string or `[{ msg }]` — `handleResponse` in `services/api.ts` handles both; route all fetches through it.
7. **Ports**: backend 8000, frontend 5173.
8. **Commit messages / PR descriptions**: do not mention that they were written by Claude.
9. **Bulk row updates**: prefer a single set-based `update()` statement over loading rows and mutating them in a loop. The per-row loops in `finish_sprint` and the reconciler sweeps are deliberate exceptions (expected N ≈ 0, per-row logging, Python-side staleness/retry branching) — don't copy that pattern to paths where the row count can grow.
10. **Config-derived UI decisions**: never duplicate a backend config constant as a frontend literal — expose a computed flag on the response model instead (e.g. `clarification_cap_reached` is a `Requirement` property serialized via `response_model`; the card reads the flag, not `MAX_CLARIFICATION_ROUNDS`).
11. **Database migrations**: whenever a table model changes (new/altered column, index, constraint), write an accompanying migration and wire it to run at app startup (alongside `init_db()` in the startup path). `create_all` only creates missing tables, so without a migration the change never reaches existing databases. Migrations must be idempotent — startup runs them on every boot.
12. **README docs stay current**: every feature that changes user-facing behavior, setup steps, commands, config, or the API surface must update the README docs (`README.md`, `backend/README.md`, `frontend/README.md`) alongside CLAUDE.md — not just CLAUDE.md.

## MCP Tools: code-review-graph

**IMPORTANT: This project has a knowledge graph. ALWAYS use the
code-review-graph MCP tools BEFORE using Grep/Glob/Read to explore
the codebase.** The graph is faster, cheaper (fewer tokens), and gives
you structural context (callers, dependents, test coverage) that file
scanning cannot.

### When to use graph tools FIRST

- **Exploring code**: `semantic_search_nodes` or `query_graph` instead of Grep
- **Understanding impact**: `get_impact_radius` instead of manually tracing imports
- **Code review**: `detect_changes` + `get_review_context` instead of reading entire files
- **Finding relationships**: `query_graph` with callers_of/callees_of/imports_of/tests_for
- **Architecture questions**: `get_architecture_overview` + `list_communities`

Fall back to Grep/Glob/Read **only** when the graph doesn't cover what you need.

### Key Tools

| Tool                        | Use when                                               |
| --------------------------- | ------------------------------------------------------ |
| `detect_changes`            | Reviewing code changes — gives risk-scored analysis    |
| `get_review_context`        | Need source snippets for review — token-efficient      |
| `get_impact_radius`         | Understanding blast radius of a change                 |
| `get_affected_flows`        | Finding which execution paths are impacted             |
| `query_graph`               | Tracing callers, callees, imports, tests, dependencies |
| `semantic_search_nodes`     | Finding functions/classes by name or keyword           |
| `get_architecture_overview` | Understanding high-level codebase structure            |
| `refactor_tool`             | Planning renames, finding dead code                    |

### Workflow

1. The graph auto-updates on file changes (via hooks).
2. Use `detect_changes` for code review.
3. Use `get_affected_flows` to understand impact.
4. Use `query_graph` pattern="tests_for" to check coverage.
